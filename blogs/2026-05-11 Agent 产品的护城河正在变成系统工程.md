# Agent 产品的护城河正在变成系统工程

> 真正能跑进生产的 Agent，不只是更聪明的模型，而是一整套围绕模型构建的运行系统。

过去一年，大家讨论 Agent，最常见的问题是：

这个模型够不够强？

它会不会调用工具？

它能不能自主完成任务？

这些问题当然重要，但最近几篇来自 Perplexity 和 Claude 的文章放在一起看，会发现一个更大的变化：

**Agent 产品的竞争，正在从模型能力竞争，转向系统工程竞争。**

模型仍然是核心，但已经不是全部。

一个真正可用的 Agent 产品，至少需要五个系统层：

- 推理层：怎么把模型又快又便宜地跑起来
- 缓存层：怎么让长程任务不被成本和延迟拖死
- 记忆层：怎么让 Agent 跨会话积累经验
- 评估层：怎么让 Agent 知道什么叫“好”
- 编排层：怎么让多个 Agent 并行完成复杂任务

如果没有这些，Agent 很容易停留在 demo 阶段。

看起来能跑，实际上跑不稳；看起来很聪明，实际上每次都从零开始；看起来省人力，实际成本和延迟很快失控。

---

## 一、推理引擎：成本战争已经深入到 GPU kernel

Perplexity 最近发布了一篇文章，讲他们如何在内部推理引擎 ROSE 中使用 NVIDIA CuTeDSL。

这篇文章技术细节很多，但核心问题很朴素：

**AI 搜索产品每天要处理大量实时请求，怎么让新模型架构快速上线，并且尽可能接近 GPU 的峰值性能？**

Perplexity 的 ROSE 不只是一个“跑模型”的服务。

它要负责 request scheduling、batching、token decoding、KV storage、prefix matching、设备初始化、权重加载、跨设备通信等一整套运行时工作。

换句话说，模型只是其中一部分。真正决定生产效率的，是模型周围的推理系统。

这也是为什么 Perplexity 要关注 CuTeDSL 这种底层 GPU 编程工具。

很多 inference kernel 的数学并不复杂，难的是让硬件以最合适的方式执行。尤其是今天的模型越来越复杂：MoE、长上下文、不同 attention 机制、不同量化方式，不同阶段的 workload 也完全不一样。

比如 prefill 和 decode，就是两种不同的推理形态。

Prefill 是一次处理大量输入 token，更看重吞吐；decode 是一步步生成 token，更看重极低延迟和 memory bandwidth。一个 kernel 不可能在所有场景都最优。

MoE 也一样。

大家谈 MoE 时常说“只激活部分专家，所以更省”。但在真实系统里，MoE 的成本不只在专家计算，还在 token routing、dispatch/combine、跨卡通信、NVLink、InfiniBand、同步策略和 memory layout。

这说明什么？

**Token 成本不是价格表上的数字，而是整个系统工程能力的结果。**

未来 AI 产品如果要在大规模用户面前稳定运行，只会越来越依赖自己的 inference runtime、缓存策略、kernel specialization 和硬件利用率。

这不是研究论文里的漂亮指标，而是每天都要付账单的生产现实。

## 二、Prompt caching：长程 Agent 的隐藏生命线

Claude Code 团队也发布了一篇很硬的工程复盘，标题里直接写着：Prompt caching is everything。

这个判断非常值得注意。

因为在很多人的理解里，prompt caching 只是一个省钱技巧。但 Claude Code 的经验是：长程 Agent 产品是否可用，很大程度上取决于 prompt cache 命中率。

Claude Code 会像监控 uptime 一样监控 cache hit rate。缓存命中率下降，不是“小优化没做好”，而是会直接影响成本、延迟和用户可用额度。

Prompt caching 的关键机制是 prefix match。

也就是说，请求开头的内容越稳定，越容易复用缓存；前缀中任何地方变化，都可能让后面缓存失效。

所以 Claude Code 的 prompt 结构会把稳定内容放前面，动态内容放后面：

- 静态 system prompt 和工具定义
- 项目级 `CLAUDE.md`
- session context
- 对话消息

这带来很多反直觉的设计。

比如，不要频繁改 system prompt。

时间变了、文件状态变了、用户偏好变了，直觉上你可能想更新系统提示。但这样会破坏缓存。更好的做法，是把动态信息放进后续 message 或 tool result 里。

再比如，不要中途增删工具。

工具定义也是缓存前缀的一部分。进入计划模式时，直觉上似乎应该只保留只读工具，但 Claude Code 反而保持工具集合稳定，把 EnterPlanMode 和 ExitPlanMode 做成工具，让模式变化通过消息表达，而不是改工具列表。

再比如，不要随便中途换模型。

一个会话如果已经在 Opus 上积累了大量缓存，中途切到 Haiku 可能反而更贵，因为要重新构建缓存。更合理的方式是用 subagent 做交接，把明确任务交给另一个模型。

这些细节共同指向一个结论：

**Agent harness 不是把模型、工具、prompt 随便接起来，而是在成本、延迟、上下文和行为之间做系统设计。**

一个成熟 Agent 产品的很多能力，用户看不见。

用户只看到它回答快、连续性好、能处理长任务。但背后其实是稳定前缀、tool loading、compaction、subagent handoff、cache-safe forking 等一整套工程策略。

## 三、记忆和 Dreaming：Agent 需要会后复盘

Claude Managed Agents 的另一篇更新文章，提到一个很有意思的新机制：dreaming。

它不是普通 memory。

Memory 更像 Agent 工作时记录经验；dreaming 更像 Agent 工作后复盘经验。

Dreaming 会定期回看过去的 agent sessions 和 memory stores，从中提取模式、整理记忆，让 Agent 在会话之间变得更好。

它能发现：

- Agent 反复犯的错误
- 多个 Agent 逐渐形成的工作流
- 团队共享偏好
- 长期任务中的稳定模式

这件事很重要。

因为真正的工作不是一次性问答，而是持续发生的。一个企业里的 Agent 如果每次都从零开始，它永远只是一个临时助手；只有当它能跨会话沉淀经验，才可能变成组织能力的一部分。

但记忆也不是越多越好。

记忆会变脏，会过时，会互相冲突，会把偶然经验误当成稳定规则。所以 dreaming 的价值不只是“增加记忆”，而是整理记忆，让它保持高信号。

这和个人知识库很像。

你不是把所有资料都扔进 Obsidian 就有知识体系了。真正有价值的是分类、链接、复盘、删减和重新组织。

Agent 也一样。

**没有整理的 memory，只是更长的噪音。经过复盘的 memory，才可能成为能力。**

## 四、Outcomes：Agent 需要知道什么叫“好”

Claude Managed Agents 这次还发布了 outcomes。

它的思路是：开发者写一个 rubric，描述什么叫成功；Agent 按这个标准工作；另一个独立 grader 在自己的上下文窗口中评估输出。如果不达标，grader 指出问题，Agent 再修改。

这听起来像一个小功能，但其实击中了 Agent 产品化的核心。

很多 Agent 失败，不是因为它不会做，而是因为它不知道什么叫做好。

写一篇文章，它不知道你的编辑标准。

做一份 PPT，它不知道你的视觉规范。

审查一份文档，它不知道哪些风险在你们团队里是红线。

写代码，它不知道你们更重视可维护性、性能，还是上线速度。

所以，Agent 需要的不只是 prompt，而是成功标准。

这也解释了为什么 Perplexity 那篇 Agent Skills 手册强调：好的 Skill 不是把命令写给模型看，而是把人的判断、边界、审美、失败案例写进去。

模型通常知道通用步骤。

它缺的是这个组织、这个场景、这个任务里“什么算对”。

Outcomes 本质上就是把“什么算对”产品化。

这会成为未来 Agent 工作流的关键模块。尤其在内容、设计、法律、金融、文档、代码审查等领域，很多质量标准不是纯客观的，但可以被 rubric 化。

**谁能更好地定义标准，谁就能让 Agent 更稳定地交付结果。**

## 五、多 Agent 编排：复杂任务开始产品化

Claude Managed Agents 还发布了 multiagent orchestration。

当一个任务太复杂，单个 Agent 很难完成时，lead agent 可以把工作拆给多个 specialist。每个 specialist 可以有自己的模型、prompt 和工具。

这和我们之前讨论的 sub-agent、agent team、异步编排是一条线。

区别在于，现在这些机制正在从工程实验走向产品化。

文章里的例子很典型：

一个 lead agent 做整体调查，同时让 subagents 分别查部署历史、错误日志、指标、支持工单。它们并行工作，共享文件系统，把结果汇总给 lead agent。

这类任务如果让单个 Agent 串行处理，会慢、会丢上下文、会被细节淹没。

多 Agent 的价值不是“显得更智能”，而是把复杂工作拆成多个可并行、可追踪、可汇总的子任务。

Netflix 用它分析大量 build logs，目标不是读完所有日志，而是找出跨大量应用反复出现的模式。

Spiral by Every 用 lead agent 接请求，再让多个 Opus subagents 并行写草稿，用 outcomes 按编辑原则和用户声音打分，只返回达标版本。

这其实非常接近人类团队的工作方式：

一个负责人定义目标，多个专家并行调查，最后回到一个判断中心。

Agent 产品正在复刻的，不是“一个超级员工”，而是“一个小型工作系统”。

## 六、真正的护城河：把模型变成可运行的组织能力

把这三篇文章放在一起看，可以看到 Agent 产品正在进入一个新阶段。

第一阶段，大家拼模型能力。

谁更会写，谁推理更强，谁工具调用更准。

第二阶段，大家拼工具连接。

能不能接浏览器、文件系统、数据库、邮件、Slack、代码仓库。

第三阶段，也就是现在正在发生的阶段，开始拼系统工程。

谁能让 Agent 更便宜、更快、更稳定、更可评估、更能积累经验、更能并行协作。

这背后的关键变化是：

**Agent 不再是一个聊天界面，而是一套运行系统。**

推理引擎决定它跑不跑得起。

Prompt caching 决定它能不能长程工作。

Memory 和 dreaming 决定它能不能积累经验。

Outcomes 决定它能不能自我校准。

Multiagent orchestration 决定它能不能处理复杂任务。

Skills 和知识层决定它能不能继承组织经验。

这些东西加起来，才是一个 Agent 产品真正的护城河。

所以，当我们再看一个 Agent 产品时，不应该只问：

它用了什么模型？

更应该问：

- 它如何管理上下文？
- 它如何控制成本？
- 它如何缓存长程任务？
- 它如何沉淀经验？
- 它如何知道什么叫好？
- 它如何拆解复杂任务？
- 它如何追踪和解释自己的工作？

这些问题的答案，才决定它能不能从 demo 走向生产。

## 结语：AI 应用会越来越像基础设施公司

过去很多 AI 应用看起来像产品公司。

做一个界面，接一个模型，设计一些工作流，就能快速上线。

但 Agent 时代会把难度往下压到系统层。

你需要懂模型，也需要懂缓存、调度、工具、权限、文件系统、评估、记忆、推理成本、硬件利用率。

这不是说每家公司都要自己写 GPU kernel。

但每个认真做 Agent 产品的人，都需要意识到：

**模型能力只是起点，系统能力才决定你能跑多远。**

未来最强的 Agent 公司，可能不是最会写 prompt 的公司，而是最会把模型变成稳定工作系统的公司。

真正的护城河，不在一次回答有多惊艳。

而在每天、每周、每月都能稳定完成复杂工作。
