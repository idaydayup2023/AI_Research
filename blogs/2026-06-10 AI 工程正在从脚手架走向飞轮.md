# AI 工程正在从脚手架走向飞轮

![封面](../covers/2026-06-10-ai-engineering-loop.png)

> AI 工程的下一阶段，不是再写一条更聪明的 prompt，也不是再堆一层更复杂的 harness，而是让每次运行都能产生下一次可验证的进步。

过去两年，AI 开发的流行词换得很快：先是 prompt engineering，后来是 vibe coding，再后来大家开始谈 harness engineering。现在，越来越多实践把焦点放到 loop。

这很容易被讲成一条新概念淘汰旧概念的时间线。但真正的变化不是“Loop 取代 Harness”，而是工程对象从一次回答、一次生成、一次任务，转向一个能持续执行、持续评价、持续积累的系统。

这篇要解决的痛点是：为什么团队已经有 prompt、skill、tool、memory、eval 和审稿流程，Agent 仍然不会越用越好？因为这些组件只是零件。只有进入循环，运行结果才会变成下一次运行的能力。

## 四个阶段，不是四次换代

先说明一个边界：agent loop、验证循环和工具反馈并不是 2026 年才出现。这里说的“范式变化”，指的是行业工程关注点正在迁移，不是四种技术按时间严格发明、依次淘汰。

Prompt engineering 解决的是：怎么把意图说清楚。

Vibe coding 把交互门槛降到很低：人描述想法、观察结果、继续说，模型快速生成和修改。它让更多人第一次感受到“自然语言可以直接驱动软件”。但它的默认单位仍是一轮轮即时反馈，质量很依赖人是否一直盯着。

Harness engineering 解决的是：怎么让模型在工具、上下文、权限、状态、验证器和错误处理的约束下可靠工作。它把偶然成功变成可重复执行。

Loop 进一步解决的是：怎么让系统在时间里收敛。

所以这四者不是替代关系，而是逐层增加工程对象：

- Prompt 管一次表达。
- Vibe coding 管人与模型的即时共创。
- Harness 管一次任务怎样可靠运行。
- Loop 管多轮运行怎样完成，以及多次运行怎样积累。

## 循环不等于多跑几遍

最危险的误解，是把 loop 当成“模型没做好，就再问一次”。

没有外部反馈的重复，只会更快地消耗 token。没有停止条件的 Ralph loop，也可能把 Agent 从提前收工推向无限返工。

Anthropic 在长时间科学计算实践中给出了一个更完整的结构：目标写在稳定指令文件里，进度和失败路径写进外置日志，参考实现和测试套件充当 oracle，Git 提供可恢复检查点。Agent 每轮不是凭感觉继续，而是根据误差、测试和未完成项决定下一步。

这类 loop 的最小单位应该是：

> 行动 -> 观察 -> 判断差距 -> 局部修复 -> 回归验证 -> 达标停止。

其中最重要的词不是“重复”，而是“差距”。每一轮都必须知道哪一项没通过，否则循环不会收敛。

## 一次任务要有内循环

Anthropic 的 generator-evaluator 实践说明，prompt 和静态 harness 都会遇到上限。突破点来自独立评价者：生成者负责产出，评价者按具体标准指出距离，再把有定位的反馈送回下一轮。

这里的评价标准决定了循环质量。

如果主编只说“文章还不够好”，下一轮大概率整篇重写，旧问题未必解决，已经写对的内容还可能回退。如果审稿意见明确到目标段落、证据、不可破坏项、验收标准和回归检查，Agent 才能像打补丁一样修订。

这与今天的旧稿 [[2026-06-10 让 Agent 返工像打补丁]] 形成衔接：那篇解决“怎么修”，Loop 进一步要求系统回答“为什么再修一轮，以及什么时候必须停”。

一个可用的任务内循环，至少需要四样东西：

- 外置状态：计划、进度、失败路径不能只留在对话里。
- 可执行反馈：测试、rubric、引用核验、差分或人工修正。
- 最小修复：只处理未通过项，冻结已经通过的部分。
- 停止条件：达到验收就结束；反复失败就升级给人，而不是无限重试。

## 多次任务要有外循环

任务做完，并不等于系统学会了。

OpenAI 与 Thrive 的税务 Agent 案例把第二层 loop 讲得很清楚。专家在真实业务中修正字段，产品记录 Agent 原值、专家修改和最终提交；重复差异经过分类，排除偏好和工作流噪声，再转成定向 eval；Codex 基于生产 trace、代码、skills 和评测调查根因，提交局部修改，并运行回归套件。

这条链路可以压缩成：

> 生产反馈 -> 结构化证据 -> 重复模式 -> Eval -> Harness 修改 -> 回放验证 -> 新的生产反馈。

这才是“自我改进”的工程版本。不是 Agent 读完自己的复盘，随手改一条规则；而是系统先证明问题重复存在，再证明修改真的改善目标，并且没有伤害已有能力。

Harness 是某一版本的工作制度。Loop 是这套制度怎样通过证据被维护。

## 编辑自动化也该这样运行

把这个范式放回每日 AI 博客和论文自动化，现有流程已经有了 harness：来源范围、筛选标准、成稿门槛、主编审稿、封面校验、关系图谱和 memory。

缺少的是明确的循环语义。

因此我把它拆成两层：

内层是单次运行闭环：`感知 -> 计划 -> 执行 -> 评价 -> 修复 -> 持久化 -> 停止`。审稿修改默认不超过三轮；同一必改项连续两轮无法关闭，就停止自动重写并交给总编判断。

外层是跨运行改进闭环：把每天的审稿修正和运行问题先结构化，检查最近七次是否重复，再决定仅记录、进入候选规则、自动应用低风险流程修改，还是等待总编确认。每次 harness 修改都要有历史回放、不可破坏项和回滚版本。

这意味着自动化不再只交付“今天写了什么”，还要交付三类状态：这次为什么可以停止，哪些问题进入下一轮，哪条经验已经从反馈变成可验证规则。

## 真正的复利来自下一次

Prompt 让模型听懂你。

Vibe coding 让你更快看到东西出现。

Harness 让 Agent 能在真实环境里可靠做事。

Loop 则提出了更高的要求：这次运行留下的证据，能不能让下一次少犯一个已经犯过的错？

所以 AI 工程的下一站，不是一个更花哨的编排名词，而是从“一次性交付系统”变成“持续收敛系统”。

好的 Loop 不会永远转。它知道何时继续、为何修复、怎样验证，也知道何时停止并把判断交还给人。

当 Harness 开始被真实反馈持续校准，脚手架才会变成飞轮。
