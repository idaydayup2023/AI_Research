# 别让 Agent 白白烧掉反馈

![封面](../covers/2026-05-30-feedback-compute.png)

Agent 接下来最贵的浪费，不是多花了 token，而是花完以后什么也没留下。

昨天我们谈的是预算分配：Agent 不该默认最高 effort、最多并发、最长上下文。今天谈的是预算花完之后的沉淀：一次高成本运行，是否把中间判断、验证结论和失败路径变成下次还能用的反馈资产。

这篇要解决的痛点很具体：当 Claude Code dynamic workflows 这类能力开始把几十到几百个 subagents 放进一个长程任务里，团队不能只问“最后结果对不对”。还要问：这次运行发现了什么、验证了什么、哪些步骤其实没必要、哪些反馈会影响下一次决策。

否则，所谓 agent 扩展只是把一次性消耗做大。

## 贵的运行必须留下东西

Claude Code dynamic workflows 的发布很有代表性。它不是简单让用户多开几个 agent，而是让 Claude 根据任务写 orchestration scripts，把复杂工程任务拆成并行 subagents，再做独立验证、汇总和交付。

官方给的场景也很清楚：代码库级 bug hunt、安全审计、大规模迁移、高风险任务复核。它甚至支持数小时、数天的长运行，并保存进度。

这类能力会改变 coding agent 的边界。过去的 AI coding 更像“快一点的助手”；dynamic workflows 更像一台临时搭建的工程组织。

但官方也提醒了一个现实问题：它会显著消耗更多 usage。

所以这里真正重要的不是“能不能让 agent 并行干活”。重要的是：一旦任务贵到这个程度，它就不应该只交付一个最终答案。

这里的“反馈资产”不是漂亮日志，而是满足三个条件的中间资产：有明确来源，能解释它改变了哪一步决策，并且下次同类任务可以被检索、复用或反驳。

它至少应该同时交付这些内容：

- 哪些假设被验证过；
- 哪些路径被排除；
- 哪些文件、接口、依赖已经被审过；
- 哪些反馈改变了后续决策；
- 哪些失败经验应该进入 runbook 或 skill。

一个昂贵 agent run，如果结束后只剩一句“已完成”，就像开了一场跨部门会议却没有纪要、没有决议、没有待办、没有复盘。

## 反馈也有质量

arXiv 新论文 [[Scaling Laws for Agent Harnesses via Effective Feedback Compute]] 提了一个很好的概念：Effective Feedback Compute。

它反对只用 tokens、tool calls、wall time 或成本来衡量 agent harness 的扩展。因为这些 raw compute 只说明系统花了多少资源，不能说明资源有没有变成有用反馈。

论文把有效反馈定义得很工程化：反馈必须 informative、valid、non-redundant，并且被 retained for subsequent decisions。换句话说，一条反馈只有在“有信息、是真的、不重复、后面还用上了”时，才算真正进入系统。

这个口径很适合放进团队的 agent 运行日志里。

不是所有测试失败都是有效反馈。重复跑同一个报错十遍，不会让系统更聪明。

不是所有搜索结果都是有效反馈。十个 subagents 都读了同一段代码，只是把重复搜索放大了。

不是所有审查意见都是有效反馈。如果 agent 看到问题但没有改变计划、没有写入状态、没有进入下一步决策，那它只是一次昂贵的旁白。

所以 Agent 扩展的第一性问题不是“还要不要加算力”，而是“这些算力有没有转成反馈资产”。

## 忙碌路径要被审计

另一个容易被忽略的问题，是 agent trajectory 里的冗余步骤。

[[Redundant or Necessary A Benchmark for Detecting Redundant Steps in Agent Trajectories]] 把这个问题单独拎出来：现在很多评测只看任务成功，却不看 agent 是怎么成功的。现实运行里，一条轨迹可能有很多看起来很努力、实际没贡献的步骤。

这对人类使用者很危险。因为 agent 的冗余不像机器空转那么明显。它会解释、会搜索、会总结、会调用工具，每一步都像在推进任务。

但从系统角度看，冗余步骤会带来四个后果：

第一，成本变高。多余工具调用和 token 会直接吃掉预算。

第二，延迟变长。长程任务里，几次没必要的探索可能把交付从分钟拖到小时。

第三，上下文变脏。冗余观察、废弃假设和重复摘要会挤占真正有用的信息。

第四，人审变难。人类 reviewer 需要从更长的轨迹里找关键判断，注意力也被浪费掉。

这就是为什么“成功率”不够。一个 agent 做成了任务，但如果路径里 40% 都是无效动作，团队还是应该把它当成可优化对象。

高成本 workflow 上线后，日志分析不该只看最终 diff、测试是否通过、报告是否完整。还要看：哪些步骤被后续引用，哪些步骤没有任何下游影响，哪些工具调用只是重复确认，哪些分支本可以提前剪掉。

## 多个局部正确，也可能组合错误

多 Agent 系统还有一个更隐蔽的问题：每个组件单独看都合理，组合起来却不合理。

[[Locally Coherent Globally Incoherent Bounding Compositional Incoherence in Multi-Component LLM Agents]] 讨论的正是这种失败。多组件 LLM agents 会让不同组件只看联合问题的一部分，再把各自判断组合起来。论文指出，局部一致不保证全局一致。

这对产品团队很有启发。

你让一个 agent 做需求理解，一个 agent 做代码搜索，一个 agent 做实现，一个 agent 做测试，一个 agent 做安全审查。每个 agent 的输出都像是对的。但它们之间的耦合约束可能没有被显式建模：需求里的权限边界是否传到了实现？代码搜索遗漏的目录是否影响安全审查？测试 agent 的假设是否和实现 agent 的改动一致？

如果这些约束只存在于自然语言 prompt 里，最后靠一个 aggregator LLM 汇总，很容易得到一种“局部可信、全局松散”的结果。

所以多 Agent harness 不能只保存每个角色的产出，还要保存角色之间的约束关系：谁依赖谁的结论，哪个假设被谁消费，哪条证据支撑了哪个动作，哪些冲突必须在合并前解决。

否则，系统看起来分工明确，实际只是把不一致分散到了不同组件里。

## 最小可行的反馈纪律

团队不需要一开始就做复杂的 EFC 指标系统。更现实的起点，是给每次高 effort agent run 加三道记录。

第一道：反馈采用记录。

每次 agent 改变计划、放弃路径、修改实现、触发人审，都要能指出“依据是哪条反馈”。没有被采用的反馈可以留下，但不能假装它提高了系统质量。

第二道：冗余步骤记录。

长程任务结束后，让 agent 或 reviewer 标出 3 类低贡献步骤：重复搜索、无效工具调用、没有下游影响的中间总结。目标不是追责，而是为下一次路由、剪枝和 skill 更新提供材料。

第三道：跨组件约束记录。

多 Agent workflow 里，至少要列出关键耦合关系：哪些角色共享同一份证据地图，哪些输出是下游输入，哪些结论需要独立验证，哪些冲突必须阻断合并。

这三道记录的意义，是把一次运行从“消费”变成“训练组织”。

不是训练模型权重，而是训练团队自己的 harness、runbook、skills、routing policy 和审查口径。

## 结尾：别只买更强的执行力

Agent 越强，越容易让团队产生一种错觉：只要给它更多 effort、更多 subagents、更多上下文，它就会自然变可靠。

这恰好是最危险的地方。

更强的执行力如果没有反馈纪律，只会更快地产生更多不可复用的过程。更贵的运行如果没有轨迹审计，只会把冗余藏在更长的日志里。更多 agent 如果没有组合约束，只会把局部合理拼成全局松散。

下一阶段的 agent 工程，不该只关心“它能不能做完”。应该关心“它做完以后，系统有没有变得更会做”。

贵的 agent run，必须留下反馈资产。
