# Agent 不会靠提示词变可靠

> 未来真正值钱的 Agent 产品，不是更会写 prompt，而是更会定义训练信号、评估标准和监督机制。

过去讨论 Agent，很多人习惯从工具开始：

能不能联网？

能不能调用浏览器？

能不能写代码、读文件、发邮件？

这些能力当然重要。但最近 Perplexity 和 Anthropic 连续几篇研究放在一起看，会发现一个更深的变化：

**Agent 的竞争正在从“能不能行动”，转向“行动之后如何被训练、被评估、被纠偏”。**

一个 Agent 如果只会调用工具，最多是一个会动的 demo。真正能进入生产，它还需要知道什么叫正确，什么叫高效，什么叫可接受，什么叫越界。

这些东西不是一句 prompt 能稳定解决的。

---

## 一、Perplexity 的 Search Agent：先定义什么叫好，再谈怎么训练

Perplexity 在《Advancing Search-Augmented Language Models》里公开了他们训练搜索增强模型的管线。

这篇文章最值得看的一点，不是用了 SFT 还是 RL，而是它承认了搜索 Agent 的目标本身就是多维的。

如果只奖励准确率，模型可能疯狂调用搜索工具，宁可多查十遍也不冒险。

如果只惩罚工具调用，模型又可能为了省步骤而牺牲可靠性。

如果只看用户偏好，模型可能写得很顺，但事实并不稳。

所以 Perplexity 的做法是：先用 SFT 固化产品底线，再用 on-policy RL 优化搜索能力。RL 数据也分成两类：一类是可验证的多跳搜索 QA，负责事实正确；另一类是 rubric-based general chat，负责格式、指令遵循和产品约束。

更关键的是 reward 设计。

他们把“正确性或 rubric 满足”作为硬门槛。只有先满足 baseline reward，偏好分和效率分才有意义。

这其实是一个非常朴素但重要的产品判断：

**Agent 不能用漂亮表达抵消事实错误，也不能用低成本抵消任务失败。**

这句话对所有 Agent 产品都成立。

内容 Agent 不能因为写得像你，就可以漏掉关键事实。

Coding Agent 不能因为 diff 很小，就可以没有通过测试。

研究 Agent 不能因为总结流畅，就可以证据覆盖不足。

Agent 需要的不是“更会说”，而是一个能把任务质量显式化的评价系统。

## 二、DRACO：真实研究任务不能只靠合成题评估

Perplexity 的另一篇 DRACO Benchmark 文章，把这个问题推到了 Deep Research 场景。

很多 benchmark 测的是单点能力：找一个事实，回答一个 trivia，解一个定义清楚的问题。

但真实用户让 AI 做研究时，任务通常不是这样的。

用户要的是跨来源综合、取舍判断、引用证据、发现遗漏、给出行动建议。答案不只是“对或错”，还涉及完整性、客观性、覆盖面和引用质量。

所以 DRACO 强调 production-grounded evaluation：用真实用户复杂研究任务来评估 deep research agents。

这对内容生产尤其有启发。

如果我们让 Agent 帮公众号做选题、资料收集和初稿生成，不能只问它“写得像不像”。真正重要的是：

- 是否覆盖了关键来源？
- 是否识别了不同文章之间的关系？
- 是否只是资讯摘要，还是形成了新观点？
- 是否引用了足够可靠的一手材料？
- 是否避免把旧观点重复包装成新稿？

这正是这个 Obsidian 工作流现在要做的事：不是抓到一篇新文章就改写，而是先放回旧摘录、旧稿和主题簇里判断。

Agent 做研究，最怕的不是不会写，而是没有标准地写。

## 三、Anthropic 的 Teaching Claude why：只教动作不够，要教原因

Anthropic 的《Teaching Claude why》从安全训练角度讲了同一个问题。

他们用 agentic misalignment 做案例：过去模型在一些虚构压力场景里会出现严重不当行为。后来 Anthropic 发现，直接在评估分布上训练正确行为，能降低特定题目的坏行为，但不一定能泛化到分布外。

更有效的方式，是教 Claude 为什么某些行为更好。

也就是说，不只是给模型一堆“正确示范”，而是让它理解背后的原则、角色和约束。

这对应用层 Agent 非常重要。

我们写 Skill、rubric、SOP、工作流时，常见错误是只列步骤：

第一步查资料，第二步总结，第三步写文章。

但真正能提升泛化能力的是原则：

什么样的来源更可信？

什么情况下应该跳过营销稿？

什么时候应该补充旧稿，而不是新开一篇文章？

什么叫“高价值”？

什么叫“重复”？

这也是 Perplexity Agent Skills 手册反复强调的：好的 Skill 不是命令清单，而是人的判断、边界和失败案例。

模型通常知道通用步骤。它缺的是具体场景里“为什么这样做才算对”。

## 四、Automated Alignment Researchers：连“AI 做研究”也要被评估

Anthropic 的 Automated Alignment Researchers 研究看起来更前沿，但它指向的问题很现实：

如果 AI 开始帮助我们做研究、写代码、设计训练方法、提出评估方案，那谁来监督它产出的“方法”是否真的有效？

Anthropic 的实验里，AARs 在某些任务上表现不错，甚至能恢复相当一部分 performance gap。但他们也特别提醒：这些方法必须在 held-out datasets 上压力测试。一个自动研究员在当前任务上找到高分技巧，不代表它提出了可泛化的真方法。

这点和今天很多 Agent 产品的风险很像。

Agent 会很快找到“让评估通过”的路径，但那条路径不一定是我们真正想要的能力。

所以未来的 Agent 系统不仅要评估输出，还要评估过程、策略和泛化。

这就是 scalable oversight 的现实版本：当模型越来越能做复杂工作，人类不可能逐行检查每一步，只能设计更好的监督结构，让系统自己暴露风险、接受复核、在新场景里证明能力。

## 五、Agent 产品的护城河，是评价体系

昨天那篇《Agent 产品的护城河正在变成系统工程》讲的是推理、缓存、记忆、编排、outcomes。

今天这些新文章补上的，是更底层的一层：

**系统工程的核心不是把模型跑起来，而是让模型在明确标准下持续变好。**

Search Agent 需要 reward。

Deep Research 需要 benchmark。

Alignment 需要原则训练。

自动研究员需要 held-out 压力测试。

Coding Agent 需要测试、diff review 和人类验收。

内容生产 Agent 也一样，需要资料覆盖、观点新意、历史脉络和引用标准。

所以以后判断一个 Agent 产品，不应该只问：

它接了哪些工具？

而要问：

- 它怎么定义成功？
- 它怎么发现失败？
- 它怎么防止奖励黑客？
- 它怎么处理分布外场景？
- 它怎么把人的判断写进系统？
- 它怎么证明自己不是只在 demo 里有效？

Agent 时代，prompt 仍然有用，但 prompt 不是护城河。

真正的护城河，是把“什么叫好”工程化。

谁能定义更好的训练信号、评估标准和监督机制，谁才能让 Agent 从会动，变成可靠。
