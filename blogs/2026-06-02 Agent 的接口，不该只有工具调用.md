# Agent 的接口，不该只有工具调用

![封面](../covers/2026-06-02-agent-interface-primitives.png)

工具调用正在变成 Agent 的旧接口。

这句话听起来有点反直觉。过去两年，我们一直在教模型调用搜索、数据库、浏览器、文件系统、MCP server。问题是，当任务变长、证据变多、状态会回滚、多个分支要合并时，“给 Agent 一个工具”很快就不够了。

这不是说工具调用不重要，而是说粗粒度工具端点只能解决“能不能接入外部世界”，解决不了长任务里的证据治理、状态治理和经验治理。

真正的瓶颈不是 Agent 没有工具，而是工具把太多中间过程藏起来了。Agent 只能发请求、等结果、把一大坨返回塞进上下文，然后继续猜。它看不到检索怎么展开，状态怎么保存，哪些路径已经证明危险，专家经验如何被版本化修正。

今天几篇新材料放在一起，给出一个更清楚的方向：下一代 Agent 接口，不是更多工具按钮，而是更低一层的可编排 primitives、显式状态和可审计技能。

这也和昨天那篇 Reharnessing 不一样：昨天讨论的是 Agent 如何在受控边界里提出修改自己的 harness；今天讨论的是外部接口层本身该如何设计，才能让 Agent 管理检索、上下文、轨迹和技能，而不是只调用一个个黑箱工具。

## 搜索要拆开

Perplexity 的 Search as Code 很有代表性。它不再把搜索当成一个固定 API：输入 query，输出结果。而是把检索、排序、过滤、fan-out、去重、渲染和中间状态暴露成 SDK primitives，让模型在 sandbox 里生成代码来组装自己的搜索管线。

这不是把搜索 API 包进 Python。关键变化是控制权下沉了。

在复杂任务里，Agent 可能要先按来源类型展开查询，再统计哪些厂商或年份覆盖不足，再生成补充查询，最后验证某条证据是否真的把 CVE 绑定到具体修复版本。这样的流程如果全部通过函数调用往返模型上下文，会产生大量噪声、延迟和成本。放到代码里，反而更像工程系统：并发、过滤、聚合、校验都由 deterministic runtime 执行，模型只负责判断策略。

这也解释了为什么“工具越多越好”是个误导。工具如果只暴露一个粗端点，Agent 得到的是黑箱结果；primitives 如果暴露得足够清楚，Agent 才能把任务策略写进执行过程。

## 上下文要适配人

另一个材料是 AdaCoM。它研究长程 web search 和 deep research 中的上下文管理：不是让 Agent 自己无限塞历史，也不是套一个固定 summarizer，而是训练一个外部 context manager，为冻结的 Agent 动态保留任务约束、进度和关键证据，剪掉过时内容。

最有意思的是它提出了一个 Fidelity-Reliability Trade-off：强 Agent 更适合保留高保真上下文，弱 Agent 反而需要更激进压缩，否则会被过多材料拖出可靠推理区间。

这对产品设计很重要。我们常把 context engineering 说成“怎么给模型更多上下文”，但真正的问题是：这份上下文给谁用？

同一份证据，对强模型是线索，对弱模型可能是噪声。一个 Agent 需要完整推理轨迹，另一个 Agent 只需要当前约束和下一步动作。上下文不是公共仓库，而是执行者适配层。

## 状态要能被看见

LongDS-Bench 把这个问题放进数据分析场景。真实数据分析不是一次问答，而是多轮迭代：变量会复用，分析口径会改变，分支会回滚，多个状态还要组合。

论文构造了 68 个长程多轮数据分析任务。结果并不好看：最好模型平均准确率只有 48.45%，从早期轮次到后期轮次表现下降近 47 个百分点。更关键的是，增加 Agent 步数不一定改善结果。

这说明失败不一定是“还没努力够”，而是状态已经乱了。

一个常见失败现场是这样的：你让数据分析 Agent 先按地区切一版，再回滚掉异常样本，再把口径改成季度，最后比较两个分支。它每一步看起来都在工作，代码也能跑，但某个旧变量、旧过滤条件或旧口径被悄悄带回来了。最后答案很完整，只是建立在错乱状态上。

所以长任务 Agent 需要的不是更长聊天记录，而是显式状态管理：哪些状态有效，哪些状态已废弃，哪个分支从哪里来，回滚后什么不能再用。

## 轨迹要变成地图

TraceGraph 又往前推了一步。它不满足于记录单条 Agent 轨迹，而是把多个模型在同一任务上的 action-observation states 汇成共享决策图，再标出 productive core 和 trap region。

这让评测从“成功/失败”变成三个过程问题：

- Agent 有没有进入有效区域？
- 它有没有暴露在历史失败区域？
- 掉进去以后有没有 repair？

这比 pass rate 有用得多。一个模型失败，可能是没找到入口；另一个模型失败，可能是走到了正确区域但踩了已知陷阱；第三个模型虽然踩坑，却能恢复。它们需要的改进完全不同。

对团队来说，这就是把昂贵的 Agent 运行变成共享地图。下一次运行不只是读历史总结，而是能知道“这里以前很多模型都走坏了，要触发恢复策略”。

## Skill 也要可回滚

COLLEAGUE.SKILL 处理的是另一类接口：专家经验。

很多团队会把专家材料、会议记录、交付物、批注意见塞进记忆或 persona prompt，希望 Agent 学会某个人的工作方式。但这很快会变成不可审计的混合物：哪些是能力，哪些是风格，哪些是过期偏好，哪些是后来被纠正过的习惯，都搅在一起。

COLLEAGUE.SKILL 的做法是把异构痕迹蒸馏成 versioned skill package，并拆成两条轨道：capability track 保存实践方法、心智模型和决策启发式；bounded behavior track 保存沟通风格、交互规则和修正历史。这个包可以检查、调用、更新、回滚，也可以跨 agent host 安装。

这其实是在说：知识库的高级形态不是被搜索，而是被蒸馏成可执行、可纠错的技能接口。

## 别再只加工具

如果把这些材料合在一起，方向很清楚：

搜索不该只是 search tool，而要变成可编排 primitives。上下文不该只是长窗口，而要适配执行者能力。运行轨迹不该只是日志，而要变成共享决策地图。专家经验不该只是 persona，而要变成可版本化 skill。

这就是 Agent 系统从“会调用工具”走向“会管理工作面”的分界线。

工具调用解决的是接入问题：模型能不能碰到外部世界。可编排接口解决的是治理问题：模型能不能在长任务里正确地控制证据、状态、路径和经验。

所以，下一次设计 Agent，不要先问还要接哪个工具。先问四个更硬的问题：

- 这个工具背后的 primitives 是否需要暴露？
- 中间状态是否能留在 runtime，而不是污染上下文？
- 历史轨迹能否告诉下一次运行哪里危险？
- 专家经验能否被检查、修正和回滚？

Agent 真正进入生产，不是因为它多了几个按钮，而是因为它终于有了可治理的接口层。
