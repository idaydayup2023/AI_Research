# Agent 自我改进，不该只改提示词

![封面](../covers/2026-05-25-agent-runtime-repair.png)

> 真正成熟的 Agent 系统，不是会把经验写进提示词，而是知道哪些经验应该进入 skill，哪些必须进入 runtime，哪些甚至要变成可回放、可回滚的源码补丁。

很多团队做 Agent，失败一次，就往 prompt 里补一句规则。

模型漏查资料，就写“请全面检查”。工具调用错了，就写“请仔细阅读工具返回”。状态丢了，就写“请记住之前步骤”。

短期看，这很快。长期看，prompt 越来越长，规则越来越多，但系统仍然不可验证：没人知道哪条规则生效，哪类失败被真正修复，下一次换模型会不会全部失效。

这几天 arXiv 上几篇 agent 论文连在一起看，会发现一个重要转向：过去我们谈 Agent 自我改进，默认是在改文本。改 prompt，改 skill，改 memory，总结失败案例，更新 SOP。

这些当然有用。但它们只覆盖了 agent 系统的一层。很多失败并不发生在文本层，而是发生在模型和世界之间的接口层：工具结果怎么呈现，动作怎么落地，状态怎么维护，错误怎么回放，修复怎么上线。

如果失败在那里，只改提示词就像给操作系统写便利贴。

## 失败不总在模型里

我们之前讲过 [[2026-05-13 真正的AI生产力来自薄Harness和厚Skills]]：好的系统应该 thin harness, fat skills。Harness 不该无限变胖，重复判断要沉淀成可复用 skill。

但这不等于所有改进都应该写成 skill。

[[Adapting the Interface Not the Model Runtime Harness Adaptation for Deterministic LLM Agents]] 提了一个很直接的问题：很多确定性任务里，模型失败不是因为它缺知识，而是因为接口没把环境翻译清楚。

比如 observation 太含混，工具契约不稳定，动作到环境的映射不可靠，反馈信息没能帮助模型纠偏。你继续给模型补一句“请认真理解工具返回值”，帮助有限。真正要改的是 runtime harness：环境如何被呈现，动作如何被执行，轨迹如何被调节。

这篇论文里的 Life-Harness 不改模型权重，也不改评测环境，而是从失败轨迹里提取可复用的 runtime interventions。结果很有意思：只用一个模型的轨迹演化出的 harness，可以迁移到另外 17 个模型。

这说明它学到的不是某个模型的小技巧，而是环境侧结构。

## 只改 skill 会碰到天花板

[[MOSS Self-Evolution through Source-Level Rewriting in Autonomous Agent Systems]] 把问题推得更远。

它指出，很多自进化 agent 都在改文本资产：skill 文件、prompt 配置、memory schema、workflow graph。但有一类结构性失败，文本层根本碰不到。

路由逻辑写在代码里。

hook 顺序写在代码里。

状态不变量写在代码里。

dispatch、rollback、health probe 也写在代码里。

如果问题出在这些地方，让 agent 再写一段“下次注意路由顺序”并不会改变系统行为。因为真正控制行为的是 source code，不是上下文里的愿望。

MOSS 的做法不是让模型自由改生产环境，而是把自改代码变成一条 release pipeline：先收集生产失败证据，整理成可回放 batch；再让外部 coding agent 提候选补丁；然后在临时 worker 里 replay；通过用户同意 gate 后才替换容器；最后用 health probe 和 rollback 控制风险。

这才是“自我改进”应该有的工程味道。

不是模型说“我下次会更好”。

而是系统留下一个可验证补丁。

## 一个常见失败现场

想象一个企业里的报表 agent。

它每天从数据库拉数据，生成 Excel，写摘要，再发给团队。上线第一周看起来没问题，直到某天财务同事发现：当数据源多了一个新地区，agent 没报错，却把筛选范围保持在旧视图里，最后生成了一份看似完整但漏掉新地区的报表。

这不是一句 prompt 能稳定解决的问题。

你可以在 skill 里写“每次检查所有地区”，但如果工具默认返回当前 view，如果 observation 没显示筛选状态，如果 spreadsheet 写入层不会暴露遗漏维度，模型很可能继续自信地完成任务。

真正的修复应该进入 runtime：工具返回必须包含当前筛选状态；报表生成前必须跑维度覆盖检查；异常维度要中断，而不是被总结掉；这次失败要变成 replay case，未来每次改 harness 都要重新跑。

失败发生在系统接口里，修复就不能只停在文本里。

## 先把失败变成任务

这里还有一个前提：你得知道系统到底失败在哪里。

[[TerminalWorld Benchmarking Agents on Real-World Terminal Tasks]] 很适合做反面提醒。它从 80,870 条真实 terminal recordings 里反向生成任务，最后得到 1,530 个 validated tasks 和 200 个人工审阅的 Verified tasks。当前最强系统在 Verified 子集上的最高通过率也只有 62.5%。

更关键的是，它和 Terminal-Bench 这类专家构造基准的相关性很弱。

这意味着：你在漂亮 benchmark 上看起来不错，不代表真实终端工作流里也可靠。真实用户的命令、状态、路径、临时文件、错误恢复和长链操作，会暴露另一种能力缺口。

所以 agent 自我改进的第一步，不是急着写“反思总结”，而是把真实失败变成可复现任务。

没有 replay batch，自动修复就是猜。

有了 replay batch，prompt、skill、harness、source patch 才能被同一个问题反复检验。

## 改进要分层

Agent 的修复层级不能混在一起。每一层应该回答不同问题，也承担不同风险。

Prompt 只处理一次性说明、表达偏好和轻量边界，不应该承载稳定业务逻辑。

Skill 处理可复用流程、判断标准和失败案例，适合沉淀人的经验，但不应该假装能改变工具契约和状态机。

Runtime harness 处理 observation、tool contract、action realization、trajectory control，适合修复模型和环境之间的接口错配。

Source patch 处理路由、状态机、权限、回滚、调度和健康检查，适合修复结构性失败，但必须进入发布治理。

很多团队的问题，是把所有失败都压回第一层。

模型漏了，就加一句 prompt。

工具错了，就加一句 prompt。

状态丢了，也加一句 prompt。

最后 prompt 越来越长，系统越来越脆，没人知道哪条规则真的生效。

更好的做法是反过来问：

这次失败应该沉淀到哪一层？

如果是表达偏好，放 prompt。

如果是重复流程，放 skill。

如果是接口错配，改 harness。

如果是状态和控制流错误，就进源码和发布流程。

## 最小自检模板

你可以用下面 5 个问题检查自己的 agent 系统：

- 这个失败是否已经变成可回放 case？
- 这次修复是 prompt、skill、harness 还是 source patch？
- 修复后是否跑过历史失败 batch？
- 修复上线是否有人工同意、健康检查和回滚路径？
- 下次换模型时，这个修复是否仍然成立？

只要有两个问题答不上来，就不要说系统已经“学会了”。

它可能只是被你临时哄好了。

## 真正的护城河在升级路径

Agent 产品未来不会只比谁接的工具多。

工具越多，失败面越大。真正难的是：失败出现后，系统能不能判断该改哪里，并把修复放进正确层级。

这也是为什么 agent harness 会越来越重要。Harness 不是为了把所有逻辑都写死，而是为了给模型提供一个可观测、可验证、可回放、可升级的运行边界。

Prompt 让 agent 听懂任务。

Skill 让 agent 复用经验。

Runtime 让 agent 正确接触世界。

Source patch 让 agent 的失败变成系统升级。

Agent 的自我改进，不该只改提示词。

它应该像一个受控的软件发布流程：有证据，有回放，有补丁，有 gate，有回滚。

否则所谓“越用越聪明”，只是把同一个错误换一种说法再犯一次。
