# Agent 上线后，也会变老

![封面](../covers/2026-05-28-agent-lifespan-maintenance.png)

> 一个 Agent 今天能跑通，不代表它下个月还可靠。真正的生产问题不是 day-one capability，而是它在不断压缩、记忆、修订和维护之后，会不会慢慢变成另一个系统。

很多团队评估 Agent，仍然像面试新人：给一批任务，看当场能不能做对。

这当然有用，但它漏掉了一个更危险的问题：Agent 上线后不是静止的。它会积累历史、写入记忆、压缩上下文、调用旧 skill、修订事实、做周期性维护。模型权重可能没变，但系统状态已经变了。

这篇要解决的痛点很具体：如果你正在把 Agent 放进长期工作流，就不能继续拿 day-one benchmark 当上线后的长期可靠性证明。不要只问“它现在能不能完成任务”，还要问“它运行 50 次、100 次、200 次之后，可靠性会怎么变”。

## 能力会过期

新论文 [[Your Agents Are Aging Too Agent Lifespan Engineering for Deployed Systems]] 提出了一个很好的词：Agent Lifespan Engineering。

它的判断很直接：长期运行的 Agent 不是一个静态模型，而是一个持续演化的 operational system。即使模型权重冻结，agent 的有效状态也会变化，因为历史会被压缩，memory store 会增长，旧事实会被修订，维护流程会改写内部状态。

所以可靠性不只是模型快照属性，而是完整 harness 的寿命属性。

这和我们前几篇文章的脉络正好接上。[[2026-05-14 Agent 的长期记忆不是聊天记录，而是 Runbook]] 讲的是记忆应该变成可取证的经验；[[2026-05-27 Agent 的复利，不是记住更多，而是少写错经验]] 讲的是经验进入系统前要有门禁。今天要再往后走一步：即使你有了 runbook 和门禁，也要承认系统会老化。

生产里的 Agent 不是永远处在第一天。

## 老化不只一种

AgingBench 把 agent aging 拆成四类机制，很适合产品和工程团队做自检。

第一类是 compression aging。历史越长，系统越依赖压缩；压缩一旦丢掉关键约束，Agent 后面看起来仍然在执行任务，实际上已经在错误前提上工作。

第二类是 interference aging。memory 越来越多，不代表经验越来越好。旧项目、旧客户、旧环境的经验混在一起，可能让检索结果互相干扰。

第三类是 revision aging。业务事实更新了，Agent 却还沿用旧状态。它不是不知道新信息，而是新旧信息没有完成语义修订。

第四类是 maintenance aging。很多团队会让 Agent 定期整理记忆、总结经验、更新 skill library。听起来很合理，但维护动作本身也可能引入错误：合并错、删错、把临时 workaround 写成长期规则。

这四类问题共同说明一件事：Agent 失败不一定发生在“不会做任务”的那一刻。它可能是在很早之前写错了一条记忆，压缩漏掉一个前提，或把一次临时经验升级成长期策略。

## 常见失败现场

想象一个客服 Agent 已经跑了三个月。

第一周，它记住了某个客户必须走人工审批。第二周，审批流程改成自动化，但旧记录没有被修订。第三周，它遇到另一个名字相似的客户，把旧审批经验也检索出来。第四周，维护任务把几条相似记录合并成一条“高价值客户需人工审批”的规则。

从外部看，这个 Agent 仍然很勤奋：它能解释理由，能引用历史，能给出流程建议。

但它已经老化了。问题不在模型能力，而在 memory state 的演化轨迹失控。你如果只跑一组新任务，看最终答案是否过关，很可能发现不了这个慢性故障。

这就是为什么 [[Is Agent Memory a Database Rethinking Data Foundations for Long-Term AI Agent Memory]] 值得注意。它提醒我们，长期 Agent memory 不是普通数据库。正确性不在单条 record，而在 memory state 随时间演化的轨迹。

换句话说，向量库能存东西，但不能自动替你治理“哪些事实该修订、哪些经验该遗忘、哪些检索结果会改变未来行为”。

## 证据也会变脏

另一个容易被低估的问题，是上下文质量。

Perplexity 的 [[Query-Aware Context Compression for Better Snippets]] 把 snippet generation 定义为 query-aware extractive context compression：不是生成摘要，而是从候选网页里保留能支撑当前问题的原文 span，剔除广告、导航、metadata、重复和离题内容。

这个思路对 Agent 寿命管理很关键。因为长期系统一定会不断压缩上下文，压缩阶段保留了什么、删掉了什么，会直接决定后续 memory、retrieval 和 reasoning 的轨迹。

如果压缩只追求短，系统会进入 compression aging：关键证据被删掉，噪声反而留下。如果压缩会改写原文，citation fidelity 会下降，后续验证也更困难。

所以 context compression 不只是成本优化。它是 Agent 可靠性的一部分。

好的压缩应该提高 evidence density，而不是把历史变成一段看似流畅但不可核验的回忆。

## 体检也要防漂移

知道 Agent 会老化之后，下一步不是多写几条测试，而是建立定期体检。

但体检本身也有坑。[[Anchor Mitigating Artifact Drift in Agent Benchmark Generation]] 提出 artifact drift：任务指令、环境、oracle、verifier 如果由松散流程分别生成，就很容易互相不一致。结果是任务不可解、奖励可被 hack，或者 verifier 评的东西和真实业务目标不是一回事。

Anchor 的做法是从同一个参数化业务规格里生成自然语言任务、环境配置、求解器认证答案和状态 verifier。这个设计给企业 Agent 一个很现实的启发：评测环境也必须有版本化、有同源约束、有可审计终态。

否则你以为自己在做健康检查，实际上只是在检查一套已经漂移的仪表盘。

Agent 生命周期越长，评测系统越不能只靠一次性 benchmark。你需要周期性 replay、counterfactual probes、memory pipeline 分段诊断，以及对 write、retrieval、utilization 的定向修复。

## 上线后才开始

如果把这些材料合在一起，结论并不复杂：

Agent 上线不是可靠性工作的结束，而是可靠性曲线的开始。

第一天的能力评测只能回答“它现在能不能做”。寿命管理要回答的是：

- 关键事实被压缩后还在不在；
- memory 增长后是否互相干扰；
- 旧事实更新后是否真的完成修订；
- 自动维护有没有引入新错误；
- verifier 是否仍然对齐真实业务终态；
- 同一个错误答案，到底该修 write、retrieval，还是 utilization。

这套问题会让 Agent 工程从“把模型接进工具”变成“运营一个会演化的系统”。

真正可靠的 Agent，不是第一天表现最亮眼的那个，而是运行很久之后仍然知道哪些经验该保留、哪些事实该更新、哪些证据必须回到原文、哪些评测不能再信。
