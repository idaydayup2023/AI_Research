# 从流水线到持续计算系统

![封面](../covers/2026-05-18-continuous-compute-system.png)

CI/CD 没死，但“把它当流水线”这件事快不够用了。

当 AI agent 能并发开出成百上千个 PR，你会发现真正的瓶颈不在写代码，而在**把变更安全、可验证、可追责地合回主干**。继续沿用为人类节奏设计的 PR + 人工评审 + Merge Queue，会让交付系统在高峰期整体失灵：不是慢一点，是假设被改写了。

我的判断是：下一代交付体系要从“流水线”升级为 **Continuous Compute（持续计算）系统**——它更像一个持续运行的计算平台，把 CI/CD 当成高性能系统来做：缓存、增量执行、可观测与成本口径，才是底座能力。

## 失败现场：当 PR 变成洪水，系统会怎么坏

你可能已经见过雏形，只是还没把它当系统性问题：

某天你们引入 agent 自动化，把“加测试、改文档、做小重构”全部交给它。它很勤奋，一晚上开了 120 个 PR。  
白天人类评审跟不上，merge queue 开始排队，CI runner 被占满。为了“别堵住主干”，你们开始提高并发、加重试、加更多 runner。

结果第二天的真实体验是：

- **CI 通过率变低**：不是代码更差，而是资源争抢、依赖下载抖动、测试时序偶发导致 flake 暴涨。
- **重试风暴**：失败→重试→占用更多 runner→更拥堵→更多失败，像雪崩一样自激。
- **主干不再可信**：大家不敢 merge，反而把变更长期挂在分支上；最终合并难度继续上升。

这类故障的本质不是“CI 太慢”，而是你在用“流水线脚本”承受一个高性能系统才会遇到的问题：**runner 饱和、cache thrash、冷启动 build、测试爆炸、以及越来越不透明的 flakiness**（官方 session 摘要明确点名了这些 failure modes）。

## 为什么“加 runner”不是答案

传统 CI/CD 的默认前提是：

- PR 数量与分支寿命可控（接近人类节奏）；
- 评审者能在有限时间理解关键差异；
- 失败的重试次数很少，且对全局资源影响可忽略。

agent 化开发会把这三条同时打穿。于是扩容只能暂时缓解拥堵，却无法阻止系统进入“重试风暴 + merge queue 串行化瓶颈”的状态。

你需要改变的不是容量，而是**治理层**。

## Continuous Compute 到底是什么（用工程语言翻译）

把 Continuous Compute 说人话：**把交付当成一套持续运行的计算系统来设计**，而不是每次 PR 触发的一串离散任务。更重要的是，它不是一句口号——在 AI Engineer Europe 2026 的同名 talk 官方摘要里，这个方向被落到一组很具体的工程抓手：remote caching、Turbo-style Docker builds、Git-aware incrementality、workflow analytics（把 time/spend 绑定到具体 job/repo/agent）、以及更强的 observability/debugging 能力。

它至少包含两层东西：一层是“吞吐底盘”（更接近官方摘要强调的部分），另一层是“治理外延”（更接近衍生笔记/我们的推演）。

## 1）吞吐底盘：缓存、增量、可观测、成本口径

这部分最容易被低估，但也是最确定会遇到的硬问题：

- **Remote caching**：把依赖/构建产物/测试分层结果当作核心资产，否则你会在 agent 并发下被重复计算吃死。
- **Turbo-style Docker builds / 冷启动优化**：降低每个分支“从零开始构建”的固定成本。
- **Git-aware incrementality**：让系统知道“这次改动影响了什么”，从而只跑必要的那部分。
- **Workflow analytics**：把 time/spend 绑定到 job/repo/agent，才能谈预算、配额、以及“为什么今天 CI 成本翻倍”的根因分析。
- **可观测与可交互 debug**：尤其是 flake 变得不透明之后，没有可观测就没有优化空间。

## 2）治理外延：入口整形与 Agent 身份（更偏推演，但很快会变成现实）

当你真的跑到 agent 高并发的规模，很多团队会发现：只做吞吐优化还不够，系统会因为“错误的负载形状”而自激失控。这时才会出现更多治理议题（常见于衍生笔记/复盘文章）：

**入口整形（Ingress shaping / rate limiting）**：把 agent 的 PR 当成流量，做限速、分级、合并策略（batch），否则重试风暴会被放大。

**Agentic identity**：给 agent 配服务账号式身份（权限/审计/配额/追责），否则你很难在“自动化越多越危险”的边界里稳住。

## 3）一份最小可行的升级清单（你可以照着改流程）

当 agent 是生产系统的执行者，它需要像服务账号一样被治理：

- 权限（能改什么、不能改什么）
- 审计（谁触发、做了什么、为什么做）
- 配额（token/runner/重试次数/并发 PR 数）
- 责任边界（失败时怎么回滚、谁来兜底）

没有身份与审计，自动化越多，风险越大；你会在某次事故里发现“没人说得清是谁干的”。

## 4）重试与回滚：把“失败是常态”写进系统

agent 世界里，失败与重试会更频繁。系统要把它们当一等公民：

- 对 flake 的隔离与熔断：避免一条不稳定用例拖垮全局
- 对重试的预算与上限：防止自激式重试风暴
- 对回滚的默认化：让“撤销变更”像“合并变更”一样顺滑

这份清单刻意只保留“今天就能做、做了就能降风险/降成本”的东西：

给你一份可以直接贴进团队文档的最小清单：

- PR 模板三件套：`变更摘要 / 风险点 / 验证计划（要跑哪些测试、看哪些指标）`
- Agent 身份三件套：`权限范围 / 并发上限 / 重试预算`
- Merge Queue 三条硬规则：
  - “高风险变更必须人工解释关键路径”（5 行以内）
  - “同类低风险变更必须批量合并”（减少队列长度）
  - “flake 超阈值自动降级：只跑关键路径 + 进入隔离队列”

## 读者自检：你们的交付体系是不是已经“过载”

两个 Yes/No 问题：

- 你们最近一个月的 CI 失败里，有没有明显上升的“非代码原因”（资源抖动、flake、依赖下载、时序问题）？（是/否）
- 当一个 agent 一天能开 100 个 PR 时，你们能不能说清楚：它的权限、配额、审计与回滚责任分别由谁/什么来承担？（是/否）

如果第一个是“是”，第二个是“否”，那你们需要的不是更好的提示词，而是更像“持续计算系统”的交付治理。

## 结尾：CI/CD 的下一站是系统工程

Continuous Compute 不是新名词游戏，它是在告诉你：交付系统的主战场已经从脚本与工具链，转移到**资源治理、身份与审计、缓存与编排、以及失败管理**。

你依然会保留 CI/CD 的名字，但它的内核会从“流水线”变成“持续计算系统”。
