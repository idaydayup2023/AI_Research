# Agent 上生产前，先管住它的会话

![封面](../covers/2026-05-13-agent-session-discipline.png)

> Demo 的目标是让 Agent 动起来，生产的目标是让 Agent 六个月后还能被解释。

过去几天，我们连续看了几篇关于 Agent 的文章。

Perplexity 讲 Skill 如何设计、评审和维护。

Claude Code 讲 prompt caching 为什么决定成本和延迟。

Garry Tan 讲 thin harness、fat skills，真正的生产力差距来自模型外部架构。

现在又有一篇很长的 X Article《How to Build AI Agents in 2026》，它把问题进一步推到工程现场：

**生产级 Agent 的第一条纪律，不是选哪个框架，而是管住它的会话。**

很多人第一次做 Agent，脑子里想的是一个 loop：

用户给任务。

模型思考。

调用工具。

返回结果。

这个 loop 可以做 demo，但离生产还差很远。

真正麻烦的事情都发生在 loop 之外：会话变长了怎么办？探索过程污染上下文怎么办？远程 sandbox 掉线怎么办？模型半年后变了怎么办？CI 里测试通过但无法提交怎么办？一次运行三周后要复盘，却发现所有日志都被清理了怎么办？

这些问题不性感，但它们决定一个 Agent 到底是玩具，还是系统。

---

## 一、Agent 最大的敌人不是笨，而是脏

很多 Agent 失败，看起来像模型不够聪明。

其实更常见的问题是：上下文脏了。

一个长任务里，Agent 会不断读文件、跑命令、看报错、猜测原因、否定假设、再读别的文件。探索阶段的信息会疯狂进入 session history。

一开始这些信息有帮助。

半小时后，它们就变成噪声。

模型会被旧判断牵引，被中间结论误导，被已经废弃的路径吸引。等到上下文快满，系统再做 compaction，把中间内容压成摘要，关键细节又可能丢失。

这就是 session history contamination。

生产 Agent 必须承认一件事：

**会话历史不是知识库，它只是工作现场。**

工作现场可以乱，但不能一直乱。探索、验证、执行、总结，应该有边界。

这篇文章给出的解法是 task：只要一个子问题有明确交付物，并且不需要父会话的完整历史，就应该拆成 child session。子 session 可以尽情探索，最后只把浓缩结果交给父 session。

这和我们在知识库项目里做的事情很像。

`clippings` 不是直接变成公众号文章，而是先进入摘录层；公众号稿也不是简单复述某一篇，而是从多个摘录中抽取结构化观点。

好的 Agent 也一样。

不要把所有过程都塞进同一个脑子里。

要让不同层级承担不同工作。

---

## 二、Compaction 不是“总结一下”这么简单

长程 Agent 一定会遇到上下文窗口。

很多系统的处理方式是：快满了，就总结一下前文。

听起来合理，但真正危险的地方在于：总结会损失精度。

比如前面某次技术选择是：

我们选择某个库，是因为它是唯一支持某个认证流、并且能和当前 middleware 模型兼容的库。

被压缩后，可能只剩一句：

我们选择它来做认证。

意思没错，但关键理由没了。

生产里，丢掉的往往就是这种理由。

等后面 Agent 再遇到相关问题，它只知道“选了什么”，不知道“为什么选”。于是开始重新发明、重新怀疑、重新绕路。

所以这篇文章提出了一个非常朴素但重要的原则：

**关键决策要写入文件，不要只留在会话历史里。**

文件能跨 compaction 存活。

运行日志能跨会话复现。

结构化 artifact 能在三周后告诉你，当时模型用了哪个版本、跑了几轮、改了哪些文件、为什么失败。

这也是 Claude Code prompt caching 那篇文章背后的同一条逻辑：长程 Agent 的稳定性，不是靠无限上下文，而是靠稳定载体。

上下文负责当前注意力。

文件负责长期记忆。

artifact 负责审计和复现。

## 三、上生产不是让 Agent 更自由，而是给自由装边界

很多人对 Agent 的直觉是：工具越多越好，权限越大越好，模型越自由越好。

生产经验通常会把这个直觉反过来。

你需要 deny path，不只是 `.env`，还包括 `.env.local`、`config/production.yaml`、各种 staging 配置和密钥目录。

你需要固定模型，而不是永远 `auto`，否则半年后默认模型变了，同一套任务跑出的结果不可比较。

你需要在 CI 里让 Agent 先 checkout 到真实分支，否则它可以测试通过，却无法提交。

你需要保留 run artifact，因为一次坏回归最有价值的不是“失败了”，而是完整知道它怎么失败。

你还需要小心 role precedence。

session role、agent role、call-level role 如果互相覆盖，模型行为会突然变化。你以为系统不稳定，其实是身份层级混乱。

这些都不像“智能”问题。

但它们构成了智能系统的边界。

没有边界，Agent 越强，事故半径越大。

有边界，Agent 才能从一次性工具变成可维护系统。

## 四、远程 Sandbox 的瓶颈，经常不是算力

这篇文章里还有一个很实在的提醒：远程 sandbox 很好，但每次工具调用都是网络往返。

本地一次 edit-test-check 循环可能 5 秒。

如果放在远程 sandbox，每轮要三次 shell call，跑 40 轮，延迟会被放大成几分钟。

解决方案也不玄学：把检查动作批处理成脚本。

一次调用完成 format、lint、test、截取输出，而不是让模型一步一步远程敲命令。

这说明 Agent 工程有一个很有意思的反差：

越是前沿的 AI 系统，越会回到传统工程常识。

减少网络往返。

稳定接口。

批处理。

日志保留。

配置外置。

最小权限。

可复现构建。

模型是新的，但系统工程不是新的。

## 五、真正的 Agent 产品，会把变化挡在外面

Garry Tan 说 thin harness、fat skills。

Perplexity 说 Skill 要有清晰 description、示例、维护机制。

Claude Code 说 prompt caching 的关键是稳定前缀，不要中途乱改工具和模型。

这篇文章把这些观点落到了更具体的 runtime 纪律上：

handler logic 应该稳定。

变化应该被 runtime config、connector、skill、role、execution target 吸收。

当 E2B API 变了，改 connector，不改业务逻辑。

当模型升级了，改 runtime config，不改 handler。

当任务需要探索，开 child task，不污染 parent session。

当上下文会丢精度，把决策写进 workspace，不让历史消息承担全部记忆。

这就是生产级 Agent 的核心：

**把会变的东西隔离起来，让不该变的东西保持稳定。**

Demo 不需要这个能力。

因为 demo 只活一次。

生产系统需要。

因为生产系统要在不同模型、不同环境、不同执行目标、不同时间点上反复运行。

## 六、给自己的 Agent 项目一张检查表

如果你正在做 Agent，不妨先问几个问题：

我的 session history 会不会被探索过程污染？

哪些任务应该拆成 child task？

哪些关键决策现在只存在聊天记录里，应该写进文件？

compaction 发生时，哪些信息绝不能被摘要稀释？

我有没有 pin 住模型？

我的 deny path 是按文件名写的，还是按目录前缀写的？

远程 sandbox 的工具调用是否可以批处理？

每次运行有没有留下可复盘 artifact？

半年后，我能不能复现今天这次 Agent 为什么这么做？

这些问题看起来不像 AI 问题。

但它们可能才是真正的 AI 产品问题。

因为模型能力会继续提升。

会写代码、会调用工具、会看日志的模型会越来越多。

稀缺的不是“能不能动起来”。

稀缺的是：

**动起来以后，能不能被约束、被复现、被审计、被持续改进。**

这就是 demo 和生产之间的距离。

也是下一阶段 Agent 产品真正的门槛。
