# Agent 的复利，不是记住更多，而是少写错经验

![封面](../covers/2026-05-27-agent-memory-gating.png)

> 很多团队以为 Agent 会越用越聪明，是因为它会记住更多。真正的复利不在“多存”，而在每次经验进入系统之前，先判断它值不值得存、应该写到哪一层、以后能不能被验证。

Agent 系统最容易走偏的地方，是把所有历史都当资产。

跑过的任务、失败的轨迹、用户的偏好、临时的需求、改过的代码、写过的总结，全都想塞进 memory、skill 或 prompt。看起来像是在积累经验，实际上可能是在制造污染：短期噪声被写成长程偏好，一次性 workaround 被沉淀成永久流程，错误归因被反复调用。

这篇要解决的痛点很具体：当你的 Agent 开始“学习”时，最先缺的不是更大的记忆容量，而是一套经验写入门禁。5 月 25 日那篇讲的是“失败发生后应该分层修复”，今天这篇讲的是更早一步：经验进入长期系统之前，先决定它是否该留下、该写到哪里、以后怎么验收。

## 先问值不值得存

[[Personalize-then-Store Benchmarking and Learning Personalized Memory for Long-horizon Agents]] 把问题说得很直接：不同用户值得长期保存的上下文并不一样。

一个用户反复提到的行业、客户、写作口径，可能是长期记忆。另一个用户临时让 Agent 比较三款工具，可能只是一次性任务。你用同一套静态规则去写入 memory，就会把有限预算浪费在 transient interactions 上，同时漏掉真正影响长程任务的个人上下文。

论文提出 session-level storage gating，本质上就是在记忆写入前先设一道门：这次会话是否值得进入长期记忆？如果不值得，就绕过 memory operation。

这比“把对话总结得更漂亮”更重要。因为长期记忆一旦污染，后面每次检索、推理和生成都会带着旧噪声。对个人知识库也一样：不是每条好信息都值得入库，不是每次灵感都值得变成长期选题。

## 再问写到哪一层

存不存只是第一问。第二问是：如果这条经验值得沉淀，它应该写到哪里？

[[CODESKILL Learning Self-Evolving Skills for Coding Agents]] 给了一个很好的切口。Coding agent 解决任务时会留下大量轨迹：读文件、改代码、跑测试、遇错回退、重新定位问题。这些轨迹如果只是保存在日志里，价值很低；如果被粗暴总结进 prompt，也很快变成噪声。

CODESKILL 的做法是把轨迹蒸馏成 procedural skills，并维护一个 compact skill bank。更关键的是，它不把 skill 维护当成固定提示词流程，而是把“选择什么、如何抽象、如何更新、如何保持规模稳定”变成可学习的管理策略。

这和我们之前写的 [[2026-05-25 Agent 自我改进，不该只改提示词]] 是同一条线，但今天的重点更前置：经验不是天然属于 prompt、memory 或 skill。它要先被分类。

用户长期偏好，可能进 memory。

可复用工作流程，可能进 skill。

工具契约和状态呈现问题，应该改 runtime harness。

路由、权限、回滚、健康检查这类结构问题，才可能进入 source patch。

如果这道分流没有做，系统会把所有经验都写进最容易改的地方。最常见的结果就是 prompt 越来越长，memory 越来越脏，skill bank 越来越像旧日志仓库。

## 不要把经验库养成垃圾场

想象一个团队把 coding agent 接进日常开发。

第一周，agent 修了几个 bug，大家很兴奋，于是让它把每次成功经验都写进 skill。第二周，skill library 里开始出现大量规则：某个测试环境曾经要手动重启，某个接口曾经返回空值，某个文件路径曾经被误判，某个 reviewer 曾经偏好一种命名。

这些规则当时都“有用”。但一个月后，测试环境升级了，接口修了，文件路径重构了，reviewer 也换了习惯。Agent 仍然在按旧 skill 做事：先重启不该重启的服务，绕开已经修好的接口，套用过时命名，甚至为了遵守旧经验而制造新错误。

这不是 Agent 没有学习。

这是它学得太随便。

经验库最危险的状态，不是空，而是看起来很丰富但没人知道哪些仍然有效。没有写入门禁、有效期、验证反馈和清理机制，memory 和 skills 都会从资产变成垃圾场。

## Harness 才是经验流量闸门

[[From Model Scaling to System Scaling Scaling the Harness in Agentic AI]] 把这件事上升到系统层：Agentic AI 的下一阶段瓶颈，不只是 model scaling，而是 system scaling。

论文把 memory substrate、context constructor、skill-routing layer、orchestration loop、verification-and-governance layer 放在同一个 agent harness 里看。这个视角很重要：经验怎么进入系统、怎么被加载、怎么被路由、怎么被验证，不应该散落在几个脚本和提示词里。

Harness 不是胶水代码。它是经验流量闸门。

它要决定什么信息进入上下文，什么写入长期记忆，什么触发 skill，什么需要验证，什么必须人工确认，什么应该被清理。也正因为如此，论文提出 harness-level benchmark 不应只看最终任务成功率，还要看 trajectory quality、memory hygiene、context efficiency、verification cost 和 safe evolution over time。

这比单纯追求“Agent 做对了没有”更接近生产现实。因为一个 Agent 今天做对，可能是靠偶然上下文；一个 Agent 今天做错，但留下了可验证、可清理、可复用的经验，反而是在积累长期能力。

## 真正的学习要能被验收

经验写入系统后，必须能被验收。

[[LongMemEval-V2 Evaluating Long-Term Agent Memory Toward Experienced Colleagues]] 已经提醒过：长期记忆不该是聊天记录，而应该像 runbook、gotchas 和证据链。系统不仅要“想起”某件事，还要能给出为什么这条记忆相关、证据来自哪里、是否仍适用于当前环境。

CODESKILL 也有相同信号：好的 skill 不是读起来像 SOP，而是能让 frozen downstream agent 在 EnvBench、SWE-Bench Verified、Terminal-Bench 2 这类任务上拿到更好的可验证执行结果。

换句话说，经验不是写进去就算学会。

它要能在未来任务里被正确调用。

它要能提升可验证结果。

它要能被更新、合并、废弃。

如果一条经验没有验收口径，它就不应该轻易进入长期系统。否则你沉淀的不是能力，而是债务。

## 给自己的最小检查清单

做 Agent、团队知识库或个人内容生产系统时，可以用五个问题检查每条“经验”；它适用于工程团队的 agent 轨迹，也适用于个人 Obsidian 选题库、公众号素材库和长期写作记忆：

- 这条信息是长期偏好、流程方法、环境事实，还是一次性噪声？
- 它应该进入 memory、skill、harness，还是只留在当次任务日志？
- 它有没有证据来源和适用边界？
- 未来什么信号能证明它仍然有效？
- 过期、冲突或效果变差时，谁负责清理它？

只要这些问题答不上来，就先别急着写入长期记忆。

Agent 的复利不是靠保存更多历史，而是靠建立更好的经验门禁。

越强的系统，越知道哪些经验不该留下。
