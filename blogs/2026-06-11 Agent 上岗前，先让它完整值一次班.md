# Agent 上岗前，先让它完整值一次班

![封面](../covers/2026-06-11-agent-full-workday.png)

> 评测一个 Agent，不能只看它会不会做一道题，而要看它能不能把一整段工作从接单做到交付。

很多团队测试 Agent 的方式，仍然像在组织一场考试。

给它一条清楚指令，准备一个干净环境，观察它能否完成某个操作。它会不会打开页面，会不会调用工具，会不会生成正确结果，最后汇总成一个成功率。

但真实工作不是一道题。用户会补充条件，会改变目标；专业软件有隐含流程；前一步的小错会污染后面十步；Agent 还可能忘记自己已经做过什么。

这篇要解决的痛点是：当团队准备把 computer-use agent 放进业务流程时，怎样判断它是真的能上岗，而不是只会通过几个孤立测试？

此前“运行账本”讨论 Agent 在工作中要把哪些状态搬出上下文；这篇处理的是另一个环节：上岗之前，测试环境怎样证明它能在这些状态变化中完成交付。

答案是把评测单位从“任务”改成“完整工作日”。

## 会点击，不等于会工作

新发布的 Workflow-GYM 把 computer-use agent 放进专业软件里的长流程任务。评测目标不是完成一个点击或填写一张表，而是沿着多个相互依赖的阶段，交付一项有业务价值的结果。

在论文所测试的专业软件、任务集和实验配置中，即使表现最强的模型，成功率也只略高于 30%。这个数字不能外推为所有 computer-use agents 的统一水平，但它足以说明：一旦评测从局部操作扩展到完整专业流程，能力缺口会被明显放大。

真正拉开差距的，不只是识别按钮和生成动作。Agent 会遗漏工作流阶段，会让早期错误一路传播，会在长流程中偏离原始目标，也会因为不理解专业软件的业务语义而做出局部正确、整体错误的操作。

这和办公室里一个常见误判很像。

新人会做每个表格动作，不等于他能独立完成月结；会使用设计软件，不等于他能按客户要求交付整套物料；会改代码，不等于他能从 issue、实现、测试一直走到可合并版本。

局部技能是上岗条件，但完整闭环才是生产能力。

## 用户不会按脚本配合

静态 benchmark 还有一个隐含假设：用户会一次性把需求说清楚，然后安静地等待 Agent 完成。

真实用户不会这样工作。

他可能中途补充预算，发现选错对象，改变优先级，拒绝某个方案，或者从聊天切到界面操作。Agent 面对的不是固定题面，而是一段持续变化的人机协作。

VISTA 因此把模拟用户引入评测，并且进一步追问：这个模拟用户本身测得真实吗？

它不只让模拟用户通过 UI 操作，也允许 API 行为；不只统计 Agent 是否成功，也衡量模拟交互的真实性、能力覆盖和暴露失败模式的有效性。

这提醒我们，Agent 评测需要两套 eval。

一套评 Agent。另一套评测试环境有没有把 Agent 真正难受的情况逼出来。

如果模拟用户永远表达清楚、从不反悔、不会跨渠道行动，那么再高的成功率也可能只是实验室里的顺风局。

## 工作日志必须跟着走

长流程失败往往不是因为 Agent 完全不会，而是因为它只记得眼前。

一个 computer-use agent 可能已经完成客户筛选，却在十步后再次打开筛选流程；已经提交了表单，却因为没有保留阶段状态而重复点击；计划上知道下一步该做什么，落到当前截图时却点错坐标。

HiViG 这篇论文给 Agent 增加了一个历史感知、视觉落地的 critic。

它把过去动作压缩成宏观工作记录，持续告诉 Agent 已经完成了哪些成果；同时在动作真正执行前，结合当前截图检查点击位置是否和意图一致。

这相当于给 Agent 配了一位现场质检员。

质检员既要看工作日志，避免 Agent 忘记进度；也要看眼前现场，避免“计划正确、手点错了”。在网页、移动端和桌面任务中，这两层检查都带来了稳定提升。

评测不能只在任务结束后打分。对于会发送消息、修改数据、提交订单的 Agent，很多错误应该在动作发生前被拦下。

## 别只保存一条成功轨迹

如果评测单位是一整段工作，过程证据也必须升级。

只保存最终成功或失败，会丢掉最有价值的信息：Agent 在哪个阶段偏航，哪次用户变化让它失去目标，哪个实体状态没有被正确更新，哪一步虽然看似合理却破坏了后续交付。

此前 StainFlow 用实体状态变化组织 GUI Agent 的过程奖励。它不把长轨迹当成一串平均重要的截图，而是追踪任务对象如何被每个动作改变，再把关键状态和证据连接起来。

Workflow-GYM 暴露完整工作流中的失败，VISTA 生成更真实的用户扰动，HiViG 在执行前检查历史与现场，StainFlow 则把过程压成可训练、可回放的证据。

四者合在一起，形成了一套更接近生产的评测链：

> 真实工作流 -> 动态用户 -> 执行前质量门 -> 过程证据 -> 最终交付。

这比“给 Agent 多做几道题”更重要。它改变的是测试对象本身。

## 一场完整的上岗测试

团队可以从五个问题开始重做 Agent 验收。

第一，测试是不是覆盖完整业务闭环？

不要只测工具调用。至少包含接收需求、获取信息、执行操作、处理变化、验证结果和交付记录。

第二，用户会不会改变条件？

加入补充信息、反悔、模糊表达、跨渠道动作和中途确认。用户模拟器也要有真实性与覆盖率指标。

第三，系统能不能看见阶段状态？

把已完成成果、当前阶段、剩余约束和关键实体状态外置。不要要求模型从完整 transcript 里反复猜进度。

第四，高风险动作有没有执行前检查？

发送、删除、提交、付款和写回之前，既检查业务意图，也检查当前界面和实际参数。

第五，失败能不能定位和回放？

保留阶段、状态变化、用户扰动、critic 判断和最终结果。只有这样，失败才会变成下一次训练、修订和审计的材料。

这五个问题测的不是 Agent 会多少技能，而是它能否在变化中维持工作连续性。

## 真正的门槛是把班上完

Agent benchmark 正在从“会不会操作”走向“能不能承担工作”。

这个变化会让很多漂亮数字变得难看，因为完整流程会暴露局部测试看不到的阶段遗漏、目标漂移、交互脆弱性和错误传播。

但这正是评测的价值。

企业需要的不是一个在干净题面上表现聪明的模型，而是一个能在用户变化、软件约束和长程状态中完成交付的系统。

所以，Agent 上岗前，别只让它做几道题。

先让它完整值一次班。
