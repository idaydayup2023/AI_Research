# 把计划变成 Agent 团队的工作台

![封面](../covers/2026-06-08-agent-plan-workbench.png)

Agentic Engineering 最容易被误解成“多开几个 Agent 并行干活”。这只是表面。

真正的变化，是计划从人类写给自己的文档，变成了 Agent 团队共享的工作台：它记录目标、证据、约束、验收标准、历史经验和下一步动作。人在这个系统里不再是主要执行者，而是提供方向、品味、风险判断和纠偏信号的人。

这篇要解决的痛点很具体：当你同时开着 Claude Code、Codex、多个终端 session、语音输入、远程机器、个人笔记和各种 skills 时，系统很快会变成一堆热闹窗口。如果没有一个稳定的共享状态，多 Agent 并行只会把混乱放大。

6 月 3 日那篇“运行账本”讲的是把证据、预算、错误定位和个人状态从模型上下文里搬出去；今天这篇讲的是另一个对象：计划本身如何成为人、Agent、skills 和工具之间的共享控制面。前者解决“状态由谁托管”，后者解决“团队围着什么协作”。

Matt Van Horn 的这篇 X Article 值得看，不是因为里面列了 22 个工具技巧，而是它把一个高吞吐 Agent 工作流的真实形态露出来了：先计划，再执行；先研究，再计划；计划爆上下文时继续接力；人不写每一行代码，而是在结果之间不断提供信号。

## 先别急着开工

这套方法里最重要的动作，不是开 Claude Code，也不是装某个插件，而是每个任务先变成 `plan.md`。

一个模糊想法、一个 GitHub issue、一张报错截图、一段 Slack 对话，都先进入计划。Agent 不是立刻编码，而是先读代码库、找历史方案、查外部文档、整理约束，再写出要改什么、为什么这么改、哪些文件相关、验收标准是什么。

这和传统开发习惯是反过来的。过去我们常常先动手，写到卡住再回头补思路。Agentic Engineering 里，计划不是慢动作，而是让 Agent 不偷懒的约束。

没有计划的 Agent 很容易早停：看起来完成了，其实边界没查完；看起来修了 bug，其实只处理了报错表面；看起来生成了方案，其实没吃进你的代码习惯和历史判断。

有计划的 Agent 则至少留下一个可复用状态：下一轮 session 可以接着它跑，另一个 Agent 可以审它，人类也可以只看 TLDR、风险点和验收项，而不用在几百行日志里找方向。

这也是为什么 `plan.md` 不只是开发文档。它更像 Agent 团队的工作台。

## 计划也要先被计划

这篇文章里有一个特别值得迁移的技巧：做深度知识工作时，先让 Agent 写“计划的计划”。

不要一上来就说“帮我写一份战略文档”或“基于这些材料写一篇文章”。更好的说法是：我会给你一份书、一段会议 transcript、几个历史方案和当前问题；你先告诉我你准备怎么读、怎么抽取、怎么对照、怎么产出，暂时不要写成品。

这个动作会显著改变输出质量。因为直接要成品时，模型会倾向于立刻组织语言；先要计划时，它必须先设计阅读路径、证据结构和判断标准。

这对内容生产尤其重要。公众号文章最容易退化成“读完一篇材料的摘要”。要避免这种退化，就不能直接问 Agent“根据这篇文章写一篇公众号”。要先问：这篇材料相对旧稿补了什么，能反驳什么，能提供哪个新失败现场，能不能形成比单篇摘录更深的主论点。

换句话说，真正值得自动化的不是写作动作，而是成稿前的选题判断。

## 并行窗口不是并行系统

Matt Van Horn 描述的日常，是四到六个 cmux tabs 同时跑：一个写计划，一个执行另一个计划，一个做外部研究，一个修测试中发现的新 bug。

很多人看到这里，会以为关键是“多开窗口”。但多开窗口只是吞吐，系统性来自窗口之间共享状态。

如果每个 Agent 都重新搜索一遍代码库、重新理解一遍目标、重新猜一遍用户偏好，那并行只是在重复烧 token。真正有用的并行，是一个窗口产出的计划、证据、失败路径和验收标准，能被另一个窗口继承、质疑或执行。

这也解释了为什么最近很多 Agent 系统都在走同一条路：把运行账本、反馈资产、skills、记忆和工具接口搬出模型上下文。模型可以负责语义判断，但不能让每个 Agent 都在自己的聊天记录里各记各的账。

Agent 团队需要的不是更多聊天窗口，而是一张共享工作台：谁在做什么、依据是什么、哪些结论已经验证、哪些路径被排除、哪些风险需要人看。

## 人类变成信号源

这篇文章里最准确的一句话，不是某个工具名，而是一个角色转变：当你跑多个 Agent 时，你的工作不是亲自做，而是提供 signal。

这里的 signal 包括很多细小判断：这个方向更接近，那个方案太泛；这个段落保留，但语气换掉；这条路径风险最大，先验证它；这个功能不重要，砍掉；这个用户会在这里卡住，补一个状态提示。

这不是“人类被替代”，而是人的劳动形态发生变化。

过去你是手：写代码、改文案、查资料、做表格。现在你更像导演和审稿人：决定哪些结果值得继续、哪些偏差要纠正、哪些风险不能放过、哪些风格是对的。

但这也要求人更清楚自己的判断标准。如果你只会说“再好一点”“更高级一点”“不太对”，Agent 只会围着模糊反馈打转。高吞吐系统最怕低质量反馈，因为它会把低质量反馈放大成一堆看似忙碌的输出。

所以 Agentic Engineering 的关键能力，反而是人类能不能给出清晰、可执行、可复用的反馈。

## 知识库要能被调用

文章里还有一条很重要的线：笔记、会议 transcript、历史计划、自定义 skills，都在变成 Agent 可调用的长期执行层。

这和“把 Obsidian 变成知识仓库”不是一回事。静态资料再多，如果 Agent 不知道什么时候读、读完怎么用、用错怎么纠正，它仍然只是资料堆。

更有价值的是三类东西。

第一，历史计划。它保存你以前怎么拆任务、怎么判断风险、怎么设验收标准。

第二，原始 transcript。它保留会议里的语气、上下文和未被总结压扁的细节，让 Agent 能重新抽取，而不是只能吃二手摘要。

第三，自定义 skills。它把你反复做的动作变成可调用命令，让经验不只停留在“记得有这么回事”，而是能变成下一次执行的一部分。

Anthropic 那篇 Claude Code skills 经验也补上了同一个结论：高价值 skill 不是把常识写进提示词，而是把组织里的验证脚本、runbook、gotchas、canonical path 和停手条件打包成 Agent 能调用的资产。也就是说，计划负责组织一次任务，skills 负责沉淀反复出现的执行方法；两者合在一起，才让工作流不只是一次性跑完。

这也是个人知识库的下一步：不是让 AI 搜到你的资料，而是让 AI 继承你的工作方式。

## 快，也会带来新风险

这篇文章不能只当效率宝典看。里面也有两个风险信号，必须保留。

第一个是权限。作者提到跳过权限确认可以大幅提高速度。但在企业项目、高风险代码库、客户数据和财务系统里，这不是一个可以直接照搬的技巧。权限确认看似烦，很多时候正是系统最后的刹车。

真正成熟的做法不是在“每一步都确认”和“全部放开”之间二选一，而是按风险分层：低风险改动自动通过，高风险动作进入人审；读权限和写权限分开；本地实验和生产环境分开；可回滚动作和不可回滚动作分开。

第二个是注意力。Agent 让构建变得太容易以后，人会不断启动新项目、开新窗口、跑新实验。产出变多了，但不代表更接近有用户、有价值、有边界的产品。

这和很多团队现在的状态很像：Agent 不是让人少工作，而是让人更容易陷入持续执行。以前是想法太多做不完，现在是想法都能开工，于是更需要停下来问一句：这件事真的值得做吗？

## 计划是新的控制面

把这些材料放在一起，Agentic Engineering 的核心不是“会用哪些工具”，而是“如何让工具、模型、记忆、技能和人类判断围绕同一个计划工作”。

计划不只是开工前的说明。它应该同时承担五个角色：

- 任务边界：这次到底解决什么，不解决什么；
- 证据地图：哪些材料已读，哪些结论有依据；
- 执行协议：哪些文件、工具、步骤会被触碰；
- 验收标准：什么叫完成，什么情况必须停下；
- 接力状态：上下文爆掉、换 Agent、换设备后还能继续。

如果计划只是给人看的 Markdown，它很快会变成摆设。只有当计划能被 Agent 读取、执行、审查、评论、修订和复用时，它才真正成为工作台。

这也是为什么“计划层质量门”“运行账本外置”“反馈资产”“厚 skills”其实在说同一件事：Agent 的复利不是来自一次更聪明的回答，而是来自每次运行后，系统都多了一点可继承的状态。

## 结尾：别把 Agent 团队变成热闹窗口

下一阶段的个人生产力和工程组织，不会只比谁的模型更强、谁开的 Agent 更多。

真正的差异会在共享状态上：你的 Agent 能不能读懂历史计划，能不能复用旧证据，能不能继承会议上下文，能不能调用稳定 skills，能不能知道哪些动作需要人类信号，能不能在权限边界内高速运行。

如果没有这些东西，多 Agent 只是一堆热闹窗口。

如果有这些东西，计划就不再是文档，而是 Agent 团队的工作台。
