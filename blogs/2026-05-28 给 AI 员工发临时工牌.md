# 给 AI 员工发临时工牌

![封面](../covers/2026-05-28-agent-temporary-credentials.png)

Agent 安全最容易被讲窄：好像只要防提示注入、过滤危险输出、让模型“别乱来”，就算进入安全区。

但真正上生产以后，问题会换一个样子：**不是 Agent 值不值得信任，而是它每一步行动的权限是谁发的、凭什么发、多久失效、出事后能不能收回。**

这篇文章想解决的痛点很直接：当团队开始把 Agent 当“AI 员工”接进代码库、工单、数据库、内部知识库和自动化流程时，安全不该再停留在模型性格层面，而要变成一套可审计的发权系统。

## 别把信任交给自觉

Claude Blog 新发的《Zero Trust for AI agents》给了一个很好的切口：面向 autonomous AI agents 的 Zero Trust，不是让模型更懂安全口号，而是把身份、意图、上下文、工具调用和输出都纳入持续验证。

这句话背后的工程含义很重。

人类员工进公司，不会因为“看起来靠谱”就拿到所有系统权限。你会给账号、角色、审批、日志、有效期、离职回收。服务账号也一样，不应该长期拿着过大的 token 在系统里到处跑。

Agent 更不能例外。因为它不是只读资料的人，而是能连续调用工具、跨系统行动、把中间结果写进 memory、把外部内容带回上下文的动态主体。它的风险不是“一次回答错”，而是拿着不该有的权限持续做事。

所以，信任 Agent 的第一步，不是相信它会守规矩，而是让它没有机会越权。

## 临时工牌，而不是万能钥匙

如果要给 Agent 一个更准确的隐喻，我更愿意说：不要给它万能钥匙，要给它临时工牌。

临时工牌有几个特征：

- 只为这次任务发放；
- 只覆盖必要系统和动作；
- 有明确有效期；
- 每次使用都会留下记录；
- 任务结束后自动回收；
- 异常时可以暂停、降级或转人工。

这和传统“给 agent 配一组 API key”的思路完全不同。长期 API key 很方便，但它把信任提前一次性发完了。真正的生产系统应该按任务切片发权：这次只读仓库，不许写；这次可以创建 PR，不许合并；这次能查客户记录，但不能导出；这次能跑迁移 dry-run，但不能执行生产迁移。

权限越接近业务核心，越不能依赖 prompt 里的“请小心”。

## 失败现场：一个看起来很勤快的 Agent

想象一个内部运维 Agent，被授权处理线上告警。

某天它收到支付失败率升高的告警，开始自动排查。它查日志、看监控、读最近发布记录，发现某个配置可能有问题。为了“快速恢复”，它调用工具回滚了配置，又重启了几个服务。

十分钟后，支付恢复了一部分，但另一个地区的用户开始出现重复扣款。复盘时团队发现：Agent 的判断链路没有完整记录；它为什么选择回滚而不是降级，没人说得清；它是否有权重启那几个服务，也没人提前定义；更麻烦的是，它把一次临时 workaround 写进了后续 runbook，下一次类似告警又准备照做。

这不是模型坏。

这是系统把太多信任发给了一个“勤快但没有边界”的执行者。

一个安全的 Agent 平台，应该在它回滚配置前就问：这次任务是否允许写生产？是否需要双人审批？是否只能先 dry-run？是否有回滚的回滚？这次动作会不会污染长期记忆？

## Sandbox 是执行边界

Claude Managed Agents 的 self-hosted sandboxes 和 MCP tunnels 说明了另一件事：Agent 安全不是只发生在模型提示词里，它发生在执行面。

self-hosted sandbox 的意义，不只是给 Agent 一个能跑命令的地方，而是让企业把网络策略、审计日志、安全工具、runtime image、资源配额都放回自己的 perimeter 里。MCP tunnels 也类似：它不是单纯“让 Agent 能访问更多工具”，而是让私有服务在边界内可达，而不是暴露到公网。

这就是 Agent 信任架构的关键拆层：

- 模型负责理解和规划；
- harness 负责路由、上下文和状态；
- sandbox 负责执行边界；
- connector/MCP 负责工具契约；
- IAM/审计系统负责身份、权限和追踪。

如果这些层混在一起，安全就会退化成“希望模型别做错”。一旦拆开，团队才有机会在每一层设闸门。

## 先建威胁模型，再自动修补

同一天那篇《Using LLMs to secure source code》也给了一个很实用的迁移方法：不要让 LLM 一上来就修漏洞，先让它建立 threat model。

这适用于安全，也适用于所有高风险 Agent 任务。

在动手前，Agent 应该先说明：资产是什么，入口在哪里，攻击者或失败模式是什么，最坏后果是什么，哪些动作不可逆，哪些地方需要人工确认。

这和今天另一篇关于 AI coding 计划层质量门的文章可以接上：计划层回答“准备怎么做”，信任层回答“允许它做到哪一步”。

一个成熟的 Agent 工作流，应该先审意图，再发权限，最后审结果。

## 给团队的五个问题

如果你已经在公司里试 Agent，可以先问五个很土但很管用的问题：

- 这个 Agent 的每次任务有没有独立身份，而不是共用长期密钥？
- 它的权限是按任务发放，还是按角色一次性发放？
- 它调用工具时，能否记录输入、输出、操作者、理由和审批状态？
- 它是否能先 dry-run，再升级到写操作？
- 它写入 memory、runbook、skill 的内容，是否有过期、回滚和人工确认机制？

如果这些问题答不上来，Agent 还不该被叫作“可信”。它只是“目前没出事”。

## 结尾：信任是一套发放机制

未来的企业 Agent，不会因为模型更强就自然可信。模型越强，越需要把信任拆成可以发放、限制、记录、回收的机制。

所以，别只问 Agent 会不会遵守规则。

先问它拿到了哪张工牌。

这张工牌能开哪扇门。

谁批准的。

什么时候失效。

出事后能不能查清、撤回、重放和修正。

Agent 安全真正要建设的，不是一个更听话的模型，而是一套不会把万能钥匙随手递出去的系统。
