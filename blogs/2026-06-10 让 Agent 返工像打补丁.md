# 让 Agent 返工像打补丁

![封面](../covers/2026-06-10-agent-revision-patch.png)

> Agent 返工最危险的，不是它没听懂意见，而是它为了修一个缺口，把已经做对的部分一起重写了。

很多人已经习惯把 AI 放进“初稿 -> 审稿 -> 修订”的工作流。

你指出三个问题，Agent 很快交回第二版。表面上，它响应了反馈；真正让人头疼的是，第二版可能修好了两个问题，又悄悄破坏了四个原本没问题的地方。事实表述变了，引用丢了，结构散了，已经确认的口径又被改回去。

这篇要解决的痛点很具体：当 Agent 开始反复修改报告、代码、方案和内容时，怎么避免“越返工，回归面越大”？

此前“反馈资产”讨论一次运行留下了什么，“计划层质量门”讨论验收标准何时进入流程；这篇只处理两者之间的修订动作：反馈已经明确之后，Agent 怎样改而不破坏已通过部分。

答案不是再写一句“请保持其他内容不变”。我们需要把 Agent 返工从重新生成，改造成增量修复。

## 自我反思不等于改进

一篇新论文专门评估 deep-research agents 收到反馈后的多轮修订。

结果很值得警惕。让 Agent 自己反思并重写报告时，它新补上的标准和被它改坏的旧标准数量接近，最终几乎没有净改善。

在论文所评估的 deep-research agent 架构与任务中，给出更具体的过程级反馈后，第一轮确实有效：分数可以提高约 8 到 15 分，反馈采纳率达到约 35% 到 40%。但这种改善没有继续复利。后续为了处理剩余缺口而重写整篇报告时，最多有 24% 已经满足的标准重新回退。

这说明 Agent 返工有两个指标。

一个是 incorporation：新意见采纳了多少。

另一个是 regression：原本做对的部分丢了多少。

只看前一个，修订就很容易制造进步幻觉。

## 整篇重写扩大了回归面

假设你让 Agent 修改一份客户方案。

第一版已经确认了客户名称、预算口径、交付周期、引用来源和风险边界。审稿人只提出一个问题：实施步骤太抽象，需要增加负责人和验收条件。

如果 Agent 的动作是“根据意见重写整份方案”，它就获得了修改所有内容的自由。即使提示词写着“其他部分保持不变”，模型仍会重新采样表达、结构和事实关系。

结果可能是步骤更具体了，但预算单位换了；负责人补上了，但某条风险被删掉；语言更顺了，但原本可核验的引用被改成了概括。

这不是模型粗心，而是修订协议给错了动作空间。

你需要的是局部补丁，系统却要求它重新生成完整文件。

## 先锁住通过项

更稳的修订流程，第一步不是把审稿意见丢给 Agent，而是把当前版本拆成三类对象：

- 已通过项：事实、引用、结构或约束已经验证，不应无故变化；
- 待修项：审稿意见明确指出的缺口；
- 依赖项：修改待修项时，可能被连带影响的段落、接口或测试。

这和软件补丁的思路很像。

修一个函数，不代表重写整个仓库。改一个接口，需要先找调用方，再跑相关测试。已经通过的测试不是背景信息，而是回归约束。

Agent 修订也应该如此。系统要明确告诉它：哪些内容被冻结，哪些位置允许编辑，修改理由是什么，哪些通过项必须重新验证。

一旦“已通过项”成为显式状态，Agent 的目标就从“写出更好的第二版”变成“在不破坏既有正确性的前提下关闭缺口”。

## 审稿单要能生成差分

很多 AI 审稿流程的问题，是审稿意见只是一段自然语言。

“论证再具体一点。”

“增加案例。”

“结构可以优化。”

这些意见对人类作者或许够用，对自动修订系统却太模糊。Agent 不知道应该改哪里、什么算完成、哪些内容禁止动，也不知道修改会影响哪些既有标准。

一张可执行的审稿单至少应该包含：

- issue：具体缺口；
- evidence：为什么判定为缺口；
- target：允许修改的段落或 artifact；
- invariant：必须保持不变的事实、引用与约束；
- acceptance check：怎样判断修订已完成；
- regression check：哪些已通过项需要复验。

Evaluation Cards 这篇论文提供了一个相邻思路：评测结果不能只给总分，还要保留可复现性、文档完整性、来源与风险、分数可比性等解释信号。

同样，审稿也不能只给“通过/不通过”。它需要成为一张能驱动差分修订的证据卡。

## 人的判断不能消失在聊天里

修订流程还有一个常见损失：人类为什么改、改了什么，最后没有留下。

CHAP，也就是 Collaborative Human-Agent Protocol，试图把人机共同工作中的 override、审批和交接变成结构化事件。一次人工修改不只留下最终文本，还留下 diff、rationale 和 content hash；一次审批也不只是聊天里说“可以”，而是能被回放的决策记录。

这个方向对内容生产和代码审查都很实用。

如果编辑把标题从 A 改成 B，系统应该知道这是因为原标题承诺过大，还是因为近期否定句式太多。如果工程师拒绝 Agent 的补丁，系统应该知道是实现错误、风险过高，还是与架构约束冲突。

否则人的判断只改变了一次结果，没有变成下一次修订可以使用的资产。

差分记录的价值，不只是审计。它还能让 Agent 逐渐学会“什么情况下应该改，什么情况下应该保持沉默”。

## 最小可行的返工协议

团队不需要先实现一套复杂协议。可以从五步开始。

第一步，保存基线版本，并固化已通过项清单与内容 hash。没有稳定比较对象，就无法判断返工到底改了什么，也无法确认原本通过的内容是否被悄悄替换。

第二步，把审稿意见改写成可定位 issue。每条意见必须指向目标位置、验收条件和不可破坏项。

第三步，只允许最小必要修改。优先提交 patch 或 section replacement，不默认生成完整新版本。

第四步，运行双向检查。既检查待修项是否关闭，也检查已通过项是否回退。

第五步，保存 diff 和理由。让后续 reviewer 能回答：为什么改、谁批准、哪些证据支持、是否需要进入规则或 skill。

这五步的重点不是限制 Agent 发挥，而是缩小无关变化。

当任务是创作初稿时，可以允许大范围探索；当任务进入返工阶段，动作空间应该收紧。初稿追求可能性，修订追求可控性。

## 返工能力决定能不能进生产

我们以前讨论过，昂贵的 Agent run 要留下反馈资产，失败轨迹要能定位错误，质量门要前移到计划层。

但这些都还缺一个中间环节：反馈如何变成不破坏既有成果的修订动作。

真实组织里的工作很少一次完成。方案要审，代码要 review，合同要改，研究报告要补证据，公众号文章也要经过主编意见。Agent 如果只擅长从零生成，不擅长稳定返工，就只能做草稿机，不能成为生产系统的一部分。

真正成熟的 Agent，不是每次都写一份看起来更好的新版本。

而是知道哪些地方已经被证明是对的，哪些地方必须改，改动会影响什么，以及如何用最小补丁关闭缺口。

让 Agent 返工像打补丁。

这可能比让它再聪明一点，更接近生产力。
