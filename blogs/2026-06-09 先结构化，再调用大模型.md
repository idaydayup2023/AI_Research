# 先结构化，再调用大模型

![封面](../covers/2026-06-09-structured-model-routing.png)

> 大模型不应该成为 AI 应用里的第一张嘴。更好的架构是：先用便宜、快速、靠近用户的模型把请求整理成结构化契约，再把真正复杂的部分交给大模型。

很多团队一做 AI 应用，就把用户输入直接丢给最强模型。

这看起来简单：少一层工程，少一套路由，少写很多 schema。问题是，原始请求往往是最脏、最含混、最没有边界的东西。你让最贵、最自由、最能行动的模型第一时间处理它，就等于把澄清、抽取、隐私过滤、权限判断、任务升级全部压在同一次推理里。

今天真正值得关注的不是“哪个模型更强”，而是 AI 应用开始学会分层用脑。

这和之前讨论的“Agent 要学会花预算”不一样。那篇文章关心的是 effort、并发、角色和人审注意力怎么分配；这篇关心的是更靠前的一步：用户的 raw text 进入大模型之前，是否已经被整理成 typed input 和可审计的任务契约。

## 第一层不是回答层

Anthropic 在 Claude Blog 里发布了一个面向 Apple Foundation Models framework 的 Swift package。表面看，这是 Claude 支持 Apple 平台开发者的新入口。

更有意思的是它暗含的工作流：Apple 的端侧模型先在 Swift 里做本地、快速的任务，比如摘要、抽取、提示生成；当请求需要多步推理、代码生成、联网搜索或数据分析时，再交给 Claude。

这里的第一层模型不是为了给出最终答案，而是为了把输入变干净。

Apple framework 可以用 `@Generable` 返回 typed Swift values。换句话说，Claude API 接到的不是一团用户自然语言，而是被应用 schema 整理过的对象：字段是什么、类型是什么、哪些信息已经抽取、哪些任务需要升级。

这比“端侧模型便宜一点”重要得多。它把小模型从低配替代品，变成了大模型前面的入口整理员。

## 原始请求太贵了

原始用户请求有三个问题。

第一，它常常不完整。用户说“帮我整理一下”，但没有说整理成什么格式、给谁看、要保留哪些口径。

第二，它常常混着权限。一个日记应用里，某段内容可以本地摘要，但跨月寻找情绪线索、关联联系人、生成外发建议，就已经进入更敏感的处理区。

第三，它常常把简单任务和复杂任务混在一起。抽取日期、识别主题、判断是否需要联网，这些不应该都交给最强模型慢慢想。

所以“先结构化”不是形式主义。它是在大模型真正介入前，先问清楚：这是什么任务、需要哪些字段、能不能本地完成、是否需要升级、升级时应该带哪些最小必要信息。

## 路由要有合同

Google 之前在 Gemini API 里把成本、延迟和可靠性做成不同服务层级，本质上是在告诉开发者：同一个智能任务，不一定应该走同一条推理路径。

但只按价格和速度路由还不够。真正可用的路由，还需要输入合同。

如果一个请求只是“请总结这段笔记”，本地模型可以直接处理。如果请求变成“找出我过去三个月反复提到但一直没有推进的计划”，系统就应该先把时间范围、数据源、隐私边界、输出对象整理出来，再决定是否调用 Claude 这种更强模型。

没有合同的路由，最后会退回 prompt 猜谜：让模型自己判断该不该升级、该带什么上下文、该不该调用工具。

有合同的路由，才可能被测试、被审计、被优化。

## 工程现场会卡在这里

一个团队做企业知识库助手，最容易犯的错是：用户问什么，就把问题、聊天历史、检索片段一股脑塞给大模型。

上线后会出现一串熟悉的问题：简单问题也很贵；复杂问题仍然答偏；用户问得含混时，模型不澄清而是硬答；涉及权限时，系统只能靠 prompt 说“注意不要泄露”；排查事故时，没人知道模型到底是因为检索错、理解错，还是任务一开始就分错了。

更稳的做法，是在大模型前面加一层低成本 preflight。

这层不追求聪明，只追求可检查：任务分类、字段抽取、敏感信息标记、上下文预算、是否需要人审、是否允许联网、是否允许调用内部系统。它输出的不是漂亮文字，而是一份结构化任务单。

大模型拿到任务单之后，再负责真正需要推理和表达的部分。

## 这也会改变产品设计

过去我们习惯把 AI 产品设计成一个输入框：用户说话，模型回答。

分层用脑之后，产品会更像一条看不见的工序链：端侧模型先处理低风险、本地、低延迟的部分；应用代码把结果变成 typed input；大模型只在任务升级时接管；工具调用和联网搜索再被放到更后面的受控阶段。

这会让 AI 产品少一点“魔法感”，但多很多工程弹性。

它也解释了为什么 CodeRabbit 要在 coding agent 前面加 structured coding plan，为什么 Managed Agents 要把 session、skills、sandbox 和状态做成版本化定义：这些都在把混乱输入转成可执行、可复核、可回滚的契约。知识层/RAG 系统越来越强调 metadata、citations 和 sufficient context，也是同一条趋势。

大家都在往同一个方向走：不要让大模型直接面对混乱世界。先把世界切成它能可靠处理的契约。

## 真正的入口是结构

这篇 Claude + Apple 的文章本身不是一个宏大的 Agent 宣言，但它指向一个很实用的判断：

未来 AI 应用的竞争，不只是谁接入了最强模型，而是谁能把用户现场变成最适合模型工作的输入层。

端侧模型、小模型、schema、typed outputs、任务路由、权限标签，这些看起来都不如大模型发布会性感。但它们决定了大模型进入应用时，面对的是一团噪声，还是一份干净的任务合同。

先结构化，再调用大模型。

这不是保守，而是让强模型真正用在该用的地方。
