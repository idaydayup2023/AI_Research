# Agent 不该拼命干活，要学会花预算

![封面](../covers/2026-05-29-agent-budget-routing.png)

Agent 系统正在进入一个很容易误判的阶段：看起来它们会越来越强，是因为模型更聪明、上下文更长、子代理更多。

但今天更值得关注的变化不是“更多”，而是“怎么花”。花多少推理 token，开多少并行 agent，重复搜索多少代码，保留多少上下文，哪个角色值得存在，哪个步骤必须让人审。

这篇要解决的痛点很具体：当 Agent 变成真实工作流，团队不能只问“它能不能做完”，还要问“它用什么预算做完”。否则你得到的不是更强的系统，而是一台会自动扩大成本、扩大噪声、扩大风险的机器。

这里的预算不只等于钱。它包括推理 effort、并发 worker、搜索次数、上下文空间、验证时间和人类审查注意力。

## 聪明不是免费资源

Claude Opus 4.8 的发布里，有一个比 benchmark 更值得看的人机接口：effort control。

用户可以在速度、rate limit 消耗和回答质量之间选择不同努力档位。Anthropic 还明确建议，对 coding 和长程异步任务使用更高 effort。

这意味着“模型多想一会儿”正在从后台参数变成产品选择。过去我们常把推理当成一个黑箱：模型要么聪明，要么不聪明；答案要么好，要么不好。现在更现实的问题是：这件事值不值得让模型多想？如果值得，应该多想到什么程度？

这不是省钱小技巧，而是 Agent 产品的控制面。

一个成熟 Agent 不应该默认把每个任务都当成最高优先级。修一个文案错别字、排查生产事故、做跨仓库迁移、重构权限逻辑，它们需要的 effort 不可能一样。如果系统不能表达这种差异，最后只能用一个粗暴默认值覆盖所有场景。

默认 effort 太低，复杂任务会失败。

默认 effort 太高，普通任务会变贵、变慢、变啰嗦。

真正可控的 Agent，需要把“努力程度”变成可分配预算。

## 并行不是多开几个窗口

Opus 4.8 同时把 Claude Code dynamic workflows 推出来：模型可以先规划任务，再在一个 session 里运行大量并行 subagents，最后做验证和汇报。

很多人会把这理解成“终于可以开更多 agent 了”。但这不是重点。

重点是：并行本身没有价值，受控并行才有价值。

如果每个 subagent 都自己读仓库、自己判断范围、自己复制文件片段、自己总结结论，多 Agent 很快会变成重复劳动放大器。它看起来很热闹，实际上只是把单个 agent 的上下文浪费复制了几十份。

arXiv 上一篇新论文 [[Long Live the Librarian! A Persistent Search Sub-Agent for Energy-Efficient Multi-Agent Software Engineering Systems]] 把这个问题说得很具体：多 Agent 软件工程系统里，多个代理会反复探索同一段代码，产生大量重复输出 token。作者提出一个持久化搜索子代理 Librarian，用共享搜索记忆记录谁看过什么、哪些文件已经探索过，并用短引用替代重复文件摘录。

结果是，在保持任务表现的同时，最多降低每个 episode 约 25% GPU 能耗。

这个数字来自论文实验语境，不应该直接外推成所有多 Agent coding 系统的通用收益。但它很好地指出了一个被低估的问题：重复搜索和重复输出本身就是系统成本。

这里的启发不是“加一个 Librarian 角色”。启发是：多 Agent 系统需要共享工作记忆。否则 agent 越多，重复看同一片世界的成本越高。

并行能力的第一道质量门，不是开多少 worker，而是这些 worker 是否共享证据地图。

## 先证明这个角色有用

另一个常见误区，是把多 Agent 架构做成组织架构图。

一个 planner，一个 researcher，一个 coder，一个 reviewer，一个 critic，一个 security auditor，一个 product manager。角色看起来完整，分工看起来合理，但没有人知道每个角色到底贡献了什么。

[[Agents that Matter Optimizing Multi-Agent LLMs via Removal-Based Attribution]] 提供了一个很实用的纠偏方式：把多 Agent 系统看成 cooperative game，用 removal-based attribution 判断每个 agent 的贡献。简单说，拿掉某个 agent，再看系统表现怎么变。

这比让 agent 自己解释“我贡献了什么”可靠得多。论文也指出，LLM 自省并不能可靠近似真实行为贡献。

这对产品团队尤其重要。多 Agent 系统不应该只做事后复盘，还应该定期做角色审计：

- 哪个 agent 拿掉后准确率下降？
- 哪个 agent 拿掉后成本下降但结果不变？
- 哪个 agent 对安全指标有贡献，但对准确率没贡献？
- 哪个 agent 只是制造更长的讨论和更高的 token 账单？

这会改变我们设计 agent workflow 的方式。过去我们倾向于先加角色，因为角色让系统看起来更专业。以后应该先设验收口径：这个角色解决什么风险？用什么指标证明它值得存在？如果拿掉它，系统会损失什么？

Agent 团队不是越像公司越好。

它越像一个可测量的执行系统越好。

## 思考也要交付压缩结果

预算不只发生在模型调用和多 Agent 编排里，也发生在上下文本身。

[[Thinking as Compression Your Reasoning Model is Secretly a Context Compressor]] 提出一个有意思的角度：reasoning model 的 thinking trace 可以被看作上下文压缩器。也就是说，模型的“思考”不只是答案生成前的中间成本，也可能把长上下文重写成任务相关的压缩表示。

这和 effort control 可以连起来看。

如果高 effort 只是生成更多废话，那它不是能力，而是浪费。如果高 effort 能把证据、约束、风险、执行路线压缩成更好的中间表示，它才值得花。

所以团队不应该只问：模型有没有多想？

应该问：它多想以后，交付了什么可复用结构？

是更清楚的计划？

是更短但更准确的证据地图？

是能被 reviewer 快速验证的风险清单？

是能被后续 agent 接力的状态摘要？

这也是为什么长上下文和长期记忆不能混为一谈。长上下文只是材料多，受控压缩才可能把材料变成可执行状态。

## 失败现场：所有人都很忙

想象一个团队把 coding agent 接进大型迁移任务。

系统启动后，planner 写了计划，几十个 subagents 同时开工。每个 agent 都很努力：读文件、搜索调用点、生成 diff、写总结。Reviewer agent 也很努力：逐条指出风险。最后主 agent 生成一份很长的汇报，看起来像一个勤奋团队忙了一整天。

但真实情况可能是：

多个 agent 反复读同一批文件。

Reviewer 审的是已经偏离目标的实现。

Security agent 只是在重复通用检查清单。

高 effort 被花在解释错误路线，而不是尽早修正路线。

最终，人类 reviewer 面对的是一大堆看似完整、实际难以验收的产物。

这就是没有预算观的 Agent 系统。它的问题不是不努力，而是不知道哪里该努力、哪里该停、哪里该共享、哪里该让人介入。

## 把预算做进 Harness

Google Gemini 3.5 的发布也在往同一个方向走。官方叙事不只是模型分数，而是“frontier intelligence with action”，面向复杂 agentic workflows、coding、长程任务和个人 AI agents。再加上 Gemini API 的 Managed Agents、Antigravity、云端 sandbox、`AGENTS.md` / `SKILL.md`，模型正在和 runtime、tooling、skills、安全边界一起发布。

这说明 Agent 竞争正在从单点能力转成系统栈能力。

预算分配应该进入 harness，而不是靠用户临时提醒：

- 任务风险决定 effort 档位；
- 代码探索结果进入共享证据地图；
- 子代理角色要能被 removal audit；
- thinking trace 要能压缩成可交接状态；
- 高风险路径先进入计划审查；
- 低价值角色、重复搜索和无效解释要被削减。

这和前几篇旧稿能接上：[[2026-05-28 AI coding 的质量门，要前移到计划层]] 讲的是先审计划；[[2026-05-27 Agent 的复利，不是记住更多，而是少写错经验]] 讲的是经验写入门禁；今天这篇补的是另一层：执行预算门禁。

Agent 不是越会干活越好。

Agent 要知道什么活值得花多少力气。

## 真正的扩展是会取舍

下一阶段的 Agent 产品，不会只比谁的模型更强、上下文更长、子代理更多。

更重要的问题会变成：

它能不能把高 effort 留给真正高风险的判断？

它能不能让并行 agent 共享已经看过的证据？

它能不能证明每个角色值得存在？

它能不能把思考压缩成别人接得住的状态？

它能不能在成本、速度、可靠性和可审查性之间做明确取舍？

这才是 Agent 从 demo 进入生产后的变化：不再迷信“多”，而是建立预算纪律。

一个不会花预算的 Agent，会把能力变成账单。

一个会花预算的 Agent，才可能把能力变成系统。
