# AI coding 的质量门，要前移到计划层

![封面](../covers/2026-05-28-upstream-planning-gate.png)

AI coding 最容易让团队误判的一点是：我们以为审查代码，就等于审查了 AI 的工作。

但代码只是最后的残影。真正决定风险的，往往发生在更早的地方：它怎么理解任务，准备改哪些模块，认为哪些边界不用碰，打算用什么测试证明自己没改坏。如果这些东西没有先被摊开，reviewer 只能在 diff 里倒推意图。

这篇要解决一个很具体的痛点：**当 coding agent 越来越快，团队不能只把质量门放在 PR 末端，而要把第一道门前移到计划层。**

## 先别急着让它改

CodeRabbit 在 Claude Blog 里的案例很值得看。它没有把 Claude 只当成“更会写代码的模型”，而是在 coding request 和 coding agent 之间加了一层：先生成 structured coding plan，团队可以在任何代码生成之前审查这个计划。

这件事听起来像流程细节，其实是产品架构判断。

传统 AI coding 的默认路径是：用户提需求，agent 改代码，reviewer 看 diff。这个流程在小任务里很爽，但一到复杂改动就会出问题。因为 diff 只能告诉你“改了什么”，很难告诉你“为什么这样改、它有没有理解错、哪些替代方案被排除了、哪些风险被忽略了”。

计划层的价值，就是把这些隐藏判断提前暴露。

在代码生成前，agent 至少应该交代五件事：任务目标、影响范围、执行步骤、风险假设、验证方式。人类审查的对象也从“这一行代码写得对不对”，变成“这条执行路线该不该被允许”。

## 最危险的是意图跑偏

AI coding 的失败不总是语法错误，也不总是测试不绿。更常见的失败是：它用一个看似合理的方案，解决了一个它误解后的问题。

比如你让 agent “优化登录态刷新逻辑”。它可能很快重构 middleware、统一异常处理、清掉重复分支。diff 看起来更干净，测试也可能通过。但如果它一开始就把目标理解成“减少分支”，而不是“保证 token 刷新失败时用户状态可恢复”，那后面的代码越漂亮，风险越隐蔽。

这就是为什么只审 diff 不够。

diff 审查关注结果，计划审查关注意图。结果错了通常容易看见，意图跑偏却经常披着合理实现的外衣。等你从几十个文件改动里发现它真正误解了什么，审查成本已经被放大了。

计划层不是为了增加仪式感，而是为了让团队在低成本阶段说“不”。

## 安全任务更要先建模型

Claude Blog 同一天还有一篇关于用 LLM 做源码安全的文章，里面的流程对普通 coding agent 也有启发：不要从 patch 开始，而要先建 threat model，再发现漏洞、验证、分流、修补。

这其实是计划层在安全场景里的版本。

安全问题如果直接让模型“帮我修漏洞”，很容易变成机械补丁：加一个校验、换一个库、补一个 if。但真正决定修复质量的是前面的建模：系统边界在哪里，核心资产是什么，攻击者入口在哪里，哪条路径后果最大，哪些现有防护不能破坏。

普通业务代码也一样。复杂任务开始前，计划里应该写清楚失败后果。权限、支付、删除、迁移、登录态、数据同步，这些路径都不该直接进入“先改再看”的模式。

让 AI 先建模型，不是因为我们不信任它写代码，而是因为我们需要先确认它在解同一个问题。

## Skill 也要能被审查

计划层解决的是“这一次怎么做”。但 agent 真正变强，还会牵涉另一个长期问题：它会把哪些经验沉淀成以后可复用的能力。

最新 arXiv 论文 MUSE-Autoskill 把 skill 定义成一个有生命周期的长期资产：创建、记忆、管理、评估、修订。它还提出 skill-level memory，让每个 skill 自己积累跨任务经验，而不是把所有经验混在一个全局记忆里。

这个方向和 Perplexity 公开的 Agent Skills 手册是同一条线。好的 skill 不是一段说明，也不是一坨提示词，而是可触发、可加载、可测试、可维护的上下文模块。

这里和计划层有一个共同点：**凡是会影响 agent 行动的东西，都应该变成可审查资产。**

计划影响本次执行，skill 影响未来复用，memory 影响长期偏好，harness 影响权限和工具边界。它们都不能只存在于模型的“感觉”里。否则团队看似拥有一个会学习的 agent，实际拥有的是一堆难以解释的隐性状态。

## 质量门该长什么样

如果把计划层落到团队流程里，不需要一开始做得很重。最小可行版本可以是一个固定的 agent preflight。

每次中高风险改动前，先让 agent 输出：

- 它认为本次任务的目标是什么；
- 它准备改哪些文件或模块，哪些明确不碰；
- 它看到的主要风险是什么；
- 它会如何验证结果；
- 它需要人确认的地方是什么。

然后团队只审这个 plan。计划不清楚，不进入代码生成；风险没说透，不进入代码生成；验证方式太空，不进入代码生成；权限边界不清，不进入代码生成。

这会牺牲一点启动速度，但能换来更重要的东西：错误在变贵之前被发现。

## 结尾：别只审产物

AI coding 的下一阶段，不是让 agent 更快地产出更多 diff，而是让团队更早地看见它准备怎么行动。

代码审查仍然重要，测试仍然重要，自动验证仍然重要。但如果第一道质量门永远放在末端，团队就会持续在结果里倒推意图。

真正可控的 AI coding 工作流，应该先审计划，再放权执行，最后审结果。

质量门越前置，agent 才越值得被放进真实工程系统。
