# 别再把 Agent Skill 当提示词了

> Perplexity 公开了一份内部手册，讲的不是怎么写更长的 prompt，而是 Agent 时代一种新的工程资产：Skill。

最近 Perplexity Research 发布了一篇文章，标题叫 **Designing, Refining, and Maintaining Agent Skills at Perplexity**。

这篇文章表面上是在讲 Perplexity 内部如何设计、评审和维护 Agent Skills，但真正有价值的地方不在“Perplexity 怎么做”，而在它把一个越来越重要的趋势说清楚了：

**Agent 的竞争力，正在从模型本身，转移到模型周围的上下文工程。**

过去我们谈 AI 应用，经常围绕三个词：

- prompt
- tool
- workflow

但 Perplexity 这篇文章讨论的是另一个更细、更工程化的层次：**Skill**。

Skill 不是一段提示词，也不是普通文档，更不是把一堆操作步骤写给 AI 看。

它更像是一个可以被 Agent 按需加载的“专业能力包”：里面有触发条件、行动原则、脚本、参考资料、模板、特殊案例和评估用例。

如果说 prompt 是你临时对模型说的一句话，那么 Skill 就是你沉淀给 Agent 的长期工作经验。

---

## 一、为什么 Skill 不是 prompt

很多人第一次看到 Skill，会本能地把它理解成“高级提示词”。

这很自然。因为它看起来确实是写给模型看的文字。

但 Perplexity 的判断非常明确：**如果你把 Skill 当成普通 prompt 或 README 来写，基本会失败。**

原因在于，Skill 不是为了“解释一个功能”，而是为了让 Agent 在正确的时机获得正确的上下文。

一个好的 Skill 至少包含四层东西。

第一，它是一个目录，而不是一个文件。

成熟的 Skill 通常不只有 `SKILL.md`，还会有：

- `scripts/`：给 Agent 直接运行的确定性脚本
- `references/`：需要时才读取的重型资料
- `assets/`：模板、schema、示例输出
- `config.json`：首次运行时的用户配置

这背后的思想很关键：**不要把所有东西一次性塞进上下文。**

Agent 的上下文窗口再大，也不是垃圾桶。Skill 的主文件应该轻，复杂内容应该分层放置，需要时再展开。

第二，它是一种格式。

Skill 的 `name`、目录名、描述字段都要严格设计。尤其是 description，它不是写给人类看的简介，而是写给模型看的路由触发器。

换句话说，description 不应该写“这个 Skill 可以做什么”，而应该写“什么时候应该加载这个 Skill”。

这是一种很不一样的写作。

你不是在写产品说明书，而是在训练一个路由器。

第三，它是可调用的。

Agent 不会每次都读完所有 Skill。系统会先把每个 Skill 的名称和短描述放进索引，模型根据用户意图判断是否加载某个 Skill。

所以 Skill 的第一个战场不是正文，而是触发。

加载太少，Agent 用不上你的能力；加载太多，Agent 会被无关上下文污染。

第四，它是渐进式的。

Perplexity 把 Skill 的上下文成本分成三层：

- 索引层：每个会话都会看到，成本最高，必须极短极准
- 加载层：Skill 主体，加载后会占用后续对话上下文
- 运行时层：脚本、参考资料、模板，只在需要时读取

这其实是 Agent 时代非常重要的产品思维：

**上下文不是免费的，注意力也不是免费的。**

## 二、每个 Skill 都是一种“税”

Perplexity 文章里有一个很好的判断：每个 Skill 都是一种 tax。

这句话值得反复看。

我们平时很容易有一种冲动：既然 Agent 可以加载 Skill，那是不是应该把所有知识都写成 Skill？

不是。

因为每多一个 Skill，系统就多一个路由选项；每多一段描述，所有会话都要为它付出上下文成本；每多一份错误的触发规则，就可能让其他 Skill 表现变差。

所以真正的问题不是“能不能写 Skill”，而是：

**没有这个 Skill，Agent 会不会稳定做错？**

如果模型本来就知道怎么做，不需要写。

如果一句 prompt 就能解决，不需要写。

如果这件事变化太快、维护跟不上，不需要写。

如果只是把一串命令写成操作手册，也不需要写。

Skill 最适合沉淀的，是模型不知道、但你知道，而且需要反复稳定复用的东西。

比如：

- 企业内部流程
- 团队的代码审查标准
- 特定行业的判断边界
- 设计审美和输出风格
- 某个复杂工具链的踩坑经验
- 某类任务的失败案例

这也是为什么 Perplexity 说，好的 Skill 需要你注入 opinion。

这里的 opinion 不是情绪化观点，而是人的判断力、品味、边界感和经验。

模型知道通用步骤，但它不知道你们团队认为什么是好，什么是坏，什么情况必须谨慎，什么失败模式最常见。

这些才是 Skill 的价值。

---

## 三、Skill 最难写的是第一行

传统软件里，我们经常说核心逻辑最难。

但在 Skill 里，Perplexity 认为最难的是 description。

因为 description 决定了这个 Skill 什么时候被加载。

坏的 description 通常会写成：

> 这个 Skill 用于监控 PR 状态、检查 CI、处理失败、提醒用户。

看起来很清楚，但对模型来说不一定好。

好的 description 更应该贴近用户真实意图：

> 当用户想让你盯住一个 PR、确保 CI 通过、持续跟进直到它能合并时加载。

差异在哪里？

前者在描述功能，后者在描述触发场景。

Agent 系统里，很多失败不是模型不会做，而是它没有在正确时间加载正确上下文。Skill 的 description 就是这道门。

所以写 Skill 的第一步不是写正文，而是写 eval。

你需要先准备一组测试问题：

- 哪些用户请求应该触发这个 Skill？
- 哪些相似请求不应该触发？
- 哪些历史失败说明这个 Skill 有必要存在？
- 哪些相邻领域容易误触发？

尤其是负例，非常重要。

因为 Skill 的最大风险往往不是“不工作”，而是“在不该出现时出现”。

一个误加载的 Skill 会污染上下文，会把 Agent 拉向错误策略，也会影响其他 Skill 的判断。

这就是 Agent 工程里很反直觉的一点：

**你不是只在优化一个 Skill，你是在优化整个 Skill 生态的路由边界。**

---

## 四、不要教模型它已经会的东西

很多人写 Skill，很容易写成这样：

先运行 A 命令，再运行 B 命令，然后执行 C，如果报错就做 D。

这对人类可能是好文档，但对模型通常是坏 Skill。

因为模型本来就知道常见命令怎么用。你把通用步骤写进去，只是在浪费上下文。

Perplexity 举了一个类似 git 的例子。

差的写法是把每个命令都列出来。

好的写法是告诉模型：

> 把这个 commit cherry-pick 到干净分支。解决冲突时保留原始意图。如果不能干净落地，解释为什么。

这句话没有逐条命令，但它给了模型更重要的东西：

- 目标
- 约束
- 判断标准
- 失败处理

这就是 Skill 写作和人类文档写作的区别。

人类文档经常补足“怎么做”。

Agent Skill 更应该补足“什么才算做对”。

因为对大模型来说，很多“怎么做”已经在训练数据里了；真正稀缺的是具体组织、具体场景、具体任务里的判断标准。

所以写 Skill 时，可以问自己一句：

**如果没有这句话，Agent 会不会做错？**

如果不会，就删掉。

## 五、Gotchas 才是最高价值内容

Perplexity 文章里最值得内容创作者和工程团队借鉴的，是它对 gotchas 的重视。

所谓 gotchas，就是那些容易踩坑的特殊情况、负面案例、边界条件。

传统文档经常重视正向流程：

第一步做什么，第二步做什么，第三步做什么。

但 Agent Skill 更重视失败模式：

- 什么情况不要这么做？
- 哪些任务看起来相似，其实不该触发？
- 哪些输出看似合理，其实违反团队标准？
- 哪些特殊案例曾经让 Agent 犯错？

Perplexity 的维护方法可以概括为一个飞轮：

- Agent 在某类场景失败，就补一个 gotcha
- Skill 被误加载，就收紧 description 并补负例
- Skill 没被加载，就补关键词和正例
- 系统提示变化，就检查冲突和重复

这意味着 Skill 不是一次写完的东西。

它更像一个持续生长的经验库。

越接近高成功率，越不是靠更长的说明，而是靠更精准的边界、更好的负例、更少的废话。

这也是为什么“让 AI 一次性生成一个 Skill”通常不靠谱。

AI 可以帮你起草，但真正让 Skill 变好的，是使用过程中的失败、评估、修订和人类判断。

模型可以消费程序性知识，但不一定能可靠生产它自己最需要的程序性知识。

## 六、Agent 时代的新工程资产

这篇文章让我想到一个更大的变化：

以前的软件资产主要是代码、文档、测试、配置。

现在 Agent 系统里，会出现一种新的资产：

**可被模型消费的工作经验。**

它不是普通知识库。

知识库回答“事实是什么”。

Skill 回答“在这个场景里应该怎么做，什么算做好，哪些坑不要踩”。

它也不是简单自动化。

自动化追求确定输入和确定输出。

Skill 面对的是开放任务，它给 Agent 提供方向、约束、工具和判断标准。

所以未来一个团队的 Agent 能力，可能不只取决于用了哪个模型，还取决于它有没有沉淀出一套高质量 Skills：

- 代码审查 Skill
- PR 跟进 Skill
- 事故复盘 Skill
- 数据分析 Skill
- 行业研究 Skill
- 公众号选题 Skill
- 客户支持 Skill
- 财务合规 Skill

这些 Skill 的质量，会直接影响 Agent 的稳定性、可控性和组织适配度。

这也是为什么 Perplexity 把 Skill quality 放到和 code quality 一样重要的位置。

模型越来越强以后，真正的问题会变成：

**你有没有把自己的经验，整理成模型能稳定调用的形式？**

---

## 结语：Skill 是给 Agent 的组织记忆

Perplexity 这篇内部手册最重要的启发，不是某个具体格式，而是一种新的工程观。

Agent 不只是调用工具的大模型。

它需要被喂给合适的上下文，需要知道什么时候加载什么能力，需要有失败案例，需要有评估，需要有维护。

Skill 就是这一整套能力的载体。

它把人的经验、审美、边界、流程和踩坑记录，压缩成 Agent 可以按需调用的模块。

所以，别再把 Skill 当提示词了。

提示词是一次性的指令。

Skill 是可以复利的组织记忆。

如果说以前的关键问题是“怎么让模型听懂我这一次要什么”，那么 Agent 时代更重要的问题会是：

**怎么让模型长期继承我已经知道的东西。**

---

## 互动时间

你觉得自己的工作里，最适合沉淀成 Agent Skill 的是哪一类任务？

是代码审查、资料研究、内容创作、客户沟通，还是某个你每周都在重复处理的流程？

如果能把这些经验变成 Skill，Agent 才不只是一个会聊天的工具，而会慢慢变成真正懂你工作方式的协作者。
