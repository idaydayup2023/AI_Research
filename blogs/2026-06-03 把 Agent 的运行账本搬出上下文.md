# 把 Agent 的运行账本搬出上下文

![封面](../covers/2026-06-03-external-agent-ledger.png)

昨天写“Agent 的接口不该只有工具调用”，解决的是外部接口要从粗粒度端点升级为可编排 primitives。今天这篇解决的是 primitives 背后的运行状态该由谁托管：真正拖垮长任务 Agent 的，常常不是工具不够多，而是它被迫在上下文里记账。

搜过哪些证据、哪些候选还没验证、什么工具调用是冗余的、哪段轨迹已经把答案带偏、哪些历史经验可以复用。这些东西如果全塞进模型 transcript，Agent 就会一边思考，一边当仓库管理员、审计员和预算员。上下文越长，账越乱；工具越多，错账越难查。

更好的方向不是继续给模型灌更多上下文，而是把可结构化的运行状态搬到系统层：让模型做语义决策，让 harness 维护证据、预算、验证、记忆和错误定位。

## 模型不该当仓库管理员

Harness-1 这篇论文的判断很直接：搜索 Agent 不能只被训练成“在不断增长的 transcript 上行动”的策略。因为在这种设计里，模型既要判断搜什么，又要记住候选文档、证据链接、验证记录、剩余约束和预算。

这等于让模型同时做两类工作：一类是语义决策，另一类是常规状态管理。前者确实需要模型能力，后者更适合系统维护。

Harness-1 的做法是把候选池、重要性标记、证据链接、验证记录、观察压缩、预算感知的上下文渲染外置到 stateful search harness。模型仍然决定搜索什么、保留什么、验证什么、何时停止，但它不再需要在自己的长上下文里维护一堆容易丢失和串味的账本。

这也是昨天那篇“接口层”之后更具体的一步：可编排 primitives 只是入口，背后还要有稳定的状态层。否则 primitives 再漂亮，最后还是会退化成一长串聊天记录。

## 工具多了，也会乱花钱

很多团队默认以为，Agent 会调用更多工具，就代表更强。但 `Learning When Not to Act` 这篇论文提醒了一个反向风险：Agentic RL 会训练出工具滥用。模型明明可以内部推理解决，却为了拿更稳的外部信号反复调用工具。

简单给工具调用加统一惩罚也不够，因为它可能压掉真正需要工具的探索。论文里的 EAPO 更接近一个预算纪律系统：在 rollout 里加入不用工具的轨迹，对简单问题重点惩罚冗余工具调用，再用置信度调整训练信号。

这件事对产品和工程很现实。工具调用不是能力本身，而是一笔预算开销：有延迟、有成本、有权限风险，也会制造更多轨迹噪声。一个成熟 Agent 不只是会调用工具，还应该学会在低风险、低不确定性场景里不行动。

这和之前的预算纪律稿是一条线，但对象更具体：以前讲 runtime 怎么分配 effort、并发、搜索和人审；这里讲训练时就要把“什么时候不该用工具”变成可学习的信号。

## 错误要定位到哪一段

Deep-research Agent 的另一个麻烦是：最终答案错了，我们常常只知道“错了”，不知道哪一步开始错。

`Where Do Deep-Research Agents Go Wrong?` 这篇论文把问题拆到 span level。它不是只给整条轨迹打分，而是把搜索、工具使用、证据检查、假设形成和答案综合拆成语义片段，再判断哪些片段真正污染了答案路径。

这比“输出错了，重跑一次”有用得多。因为长任务 Agent 里有很多看起来失败但其实无害的探索，也有一些看起来合理但会把结论带偏的 unsupported claim。真正需要修的是后者。

如果没有这种过程级错误定位，反馈资产就无法沉淀。你不知道哪段是 first error，也不知道哪段只是必要探索；下一次只能把整个长上下文重新喂给模型，让它再烧一遍预算。

## 个人工具最怕串场

MCP-Persona 则把问题带到个人应用里。MCP 让模型接入工具更容易，但接入 Reddit、小红书、飞书、Slack 这类个人和企业协作应用时，难点不是“API 能不能调”，而是身份、历史、权限、受众和本地数据库会混在一起。

这类 Agent 一旦把上下文都当成同一种记忆，就很容易串场：把 A 账号的偏好用到 B 场景，把一个团队的口径带到另一个群，把历史状态当成当前事实。

所以个人 MCP 工具的评测不能只问“工具是否可调用”，而要问：在模拟的个性化环境里，Agent 能否正确识别自己是谁、面对谁、能看什么、应该改什么、哪些历史仍然适用。

这也解释了为什么个人知识库和企业知识层不是简单的 RAG。真正的知识层要能做身份隔离、证据仲裁、状态更新和权限边界。

## 经验不是越多越好

AgentCL 进一步提醒：Agent 的长期学习也不能只看“记住了多少”。如果任务流没有设计可复用关系，我们甚至看不出记忆系统是否真的帮助了迁移。

它用受控任务流评估 continual learning：早期任务中的子解法、证据或 workflow 会被设计成后续任务可复用，再用 transfer gain 判断 Agent 是否真的从经验中受益。更重要的是，它也观察 memory-induced degradation：错误或无关经验写入后，Agent 可能变差。

这和“Agent 的复利，不是记住更多，而是少写错经验”完全同向。经验要写入系统，就必须先能过滤、合并、回放和评测。否则所谓长期记忆，只是在未来任务里埋雷。

## 真实世界还要更快

Google DeepMind 的 Running Guide agent 提供了一个具身场景里的反例：盲人和低视力跑者需要的是实时安全反馈，不是一个把所有视觉帧都丢给大模型慢慢解释的助手。

它把端侧分割模型和 Gemma 4 多模态推理拆成两条路径：低延迟安全路径负责立即停止和方向提示，高层推理路径只处理复杂场景；系统还用高信息帧选择，优先分析突发地形变化和新障碍。这里的重点不是“又一个多 Agent demo”，而是高风险 Agent 必须把安全反射、语义理解、任务规划和反馈通道分层托管。

这说明状态外置不只发生在 research agent 的证据池里，也发生在 embodied agent 的实时控制里。越接近真实世界，越不能把所有状态都塞给模型临场记。

## 万能 transcript 的现场

一个常见场景是这样的：团队做了一个 research agent，把搜索结果、工具返回、临时判断、用户偏好、历史经验、验证结论全部追加进同一个上下文窗口。刚开始效果很好，因为模型“什么都看得到”。

跑了几周后，问题开始出现：同一个结论被不同来源重复写入；旧证据没有失效标记；某次失败搜索被当成一般经验；工具调用越来越多；答案错了只能看一条巨长日志；修复方式变成“提示词里再强调一下”。

这不是提示词写得不够好，而是系统把账本、审计、预算、记忆和推理全压给了模型。模型当然会乱。

## 把账本搬出上下文

今天这批材料共同指向一个工程原则：凡是可结构化、可复核、可压缩、可复用、可审计的运行信息，都不应该长期留在模型上下文里。

候选证据要进候选池；验证记录要能被查询；工具预算要有策略；错误片段要能定位；个人状态要能隔离；历史经验要能评测迁移收益。模型要面对的是经过系统整理后的决策界面，而不是一锅越煮越浓的 transcript。

Agent 的能力边界，正在从“模型能不能想明白”转向“系统有没有把该托管的状态托管好”。这不是降低模型的重要性，而是把模型从仓库管理员、预算员和审计员这些兼职里解放出来，让它专心做真正需要语义判断的部分。
